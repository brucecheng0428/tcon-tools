# 版本號規則（全分頁一體適用）

制定日期：2026-08-02
適用範圍：`common/version.js` 裡的所有工具版號（`rxtx` / `calc` / `isp` / `aux` / `wfg` / `pattern`）與首頁 `app` 總版號
狀態：**草案，待 Bruce 確認後生效。既有版號是否回溯調整見 §5，該項未決前不要動任何現有版號。**

## 0. 為什麼要訂這個

### 實測到的不一致

統計自 `git log`（全庫 979 個 commit）與 `common/version.js`：

| 分頁 | 目前版號 | commit 數（訊息前綴法） | 每個 commit 平均進版 |
|---|---|---|---|
| `wfg` | v2.97.475 | **155** | patch +3 左右，**minor 幾乎不動**（2.97 停留很久） |
| `aux` | v2.3.1 | **22** | 混用 |
| `isp` | v1.19.0 | **16** | 幾乎每次 +1 **minor** |
| `pattern` | v1.9.0 | **10** | **每次 +1 minor** |
| `calc` | v1.5.3 | 2 | — |
| `rxtx` | v1.12.2 | 1 | — |

> 註：Bruce 手上的數字是 wfg 143 / isp 15 / aux 13，我實測是 155 / 16 / 22。差異來自部分 commit 沒用 `工具名 ` 開頭（例如 `fix(wfg):`、`ecbb640 v2.97.433:`、`chore: retry pages deploy…`），前綴法會漏掉。**結論方向不變，而且差距比原本以為的更大。**

**問題本質不是「誰對誰錯」，是兩邊往相反方向偏：**

- `wfg`：把**該進 minor 的新功能也算成 patch**。LA 通道拖曳排序、cursor 量測、韌體包管理、kvdat 匯入匯出——這些都是全新能力，卻全部塞在 `2.97.x` 裡。結果 patch 號變成「改動次數計數器」，失去語意。
- `pattern`：把**同一個功能的漸進完成拆成多個 minor**。v1.3.0 選單 → v1.4.0 編輯區連動 → v1.5.0 鍵盤 → v1.6.0 鍵盤掃描 → v1.7.0 資訊框 → v1.8.0 邊界修正，其實是「把測試畫面功能做完整」這一件事，其中 v1.6.0/v1.8.0 本質是修正而非新增能力。

### 為什麼不照抄語意化版本（SemVer）

SemVer 的 MAJOR 定義是「破壞向後相容的 API 變更」。**這裡沒有 API，也沒有任何程式會呼叫我們** — 使用者是人，用瀏覽器打開網頁。照抄那套定義的結果就是 MAJOR 永遠用不到（wfg 卡在 2.x 三年也不會有人覺得該進 3），規則等於沒訂。

所以判準要換成**對這類工具真正有意義的維度**：

> **使用者腦袋裡已經知道的事，會不會失效？**

對 FAE 工具而言，「已經知道的事」有兩種：
1. **怎麼操作**（按鈕在哪、流程是什麼）
2. **會得到什麼結果**（算出來的數字、畫出來的波形/畫面、存出來的檔案）

## 1. 規則

### 一句話判準

> **舊的東西變了 → MAJOR；多了新東西但舊的沒變 → MINOR；只是把壞的修好或內部改善 → PATCH。**

### 🔴 改動大小不是判準（2026-08-12 明文）

**「這次改很多」「這次很難做」「這次風險很高」都不會讓版號變大。** 判準只有一個：**使用者原本會的操作還在不在、要不要重新確認過去的結果。** 工程規模、投入的心力、程式碼行數一律無關（§2 案例 4 已就「重構」講過同一件事：**風險高不等於版號要大** —— 風險靠驗收條件管，不靠版號）。

對照：`wfg` 的 2.x 這一波**一路走到 `v2.97.475`** 才進 v3.0.0。中間包含 LA 通道拖曳排序、cursor 量測、韌體包管理、kvdat 匯入匯出等一整批全新能力，沒有一次進 MAJOR。**3.x 同樣可以走到 v3.9x**，只有真正需要使用者整個重新熟悉一次的大變動才進 v4。

> 這一條是兩次 v4.0.0 誤判（`pattern`、`wfg`）的共同根因：兩次都是「改動看起來很大」而不是「既有操作失效」在驅動級別。判到 MAJOR 時請先回頭確認自己是不是在用改動大小當判準 —— 並依 R2 補充停下來問 Bruce。

### 判定表

| | MAJOR（x.0.0） | MINOR（x.y.0） | PATCH（x.y.z） |
|---|---|---|---|
| **核心問句** | 使用者需要**重新學**或**重新確認結果**嗎？ | **多了**能做的事，但舊的一切照舊嗎？ | 使用者**幾乎無感**嗎？ |
| 操作流程 | 原本的按鈕**找不到了**、流程換掉 | 多了新按鈕，舊的都在原位 | 位置微調、文案、配色 |
| 既有功能的輸出 | **主動改變**（設計上決定不一樣） | 不變 | **修正為原本就該有的行為** |
| 功能增減 | **移除**既有功能 | **新增**獨立功能 | 不增不減 |
| 內部實作 | — | — | 重構、效能、資料結構改寫（**行為零改變**） |

### 三條補充規則（處理邊界情況）

**R1｜修 bug 即使畫面會變，仍算 PATCH — 但要在 CHANGELOG 標「⚠ 輸出變更」**

修 bug 是「讓行為回到本來就該是這樣」，不是主動改設計。但如果**使用者過去存下來的圖或抄下來的數字，用新版重跑會不一樣**，那他必須知道。

- 判準：修正後輸出會變 → PATCH，但 CHANGELOG 該條目**開頭必須加 `⚠ 輸出變更`**，寫清楚哪些情況下的舊結果不再成立。
- 例：本次 `pattern` 的 #3（遮罩用某些畫面時顏色跑掉）修好之後，畫面確實會變 → PATCH ＋ `⚠ 輸出變更`。

#### `⚠ 輸出變更` 的範圍定義（2026-08-09 生效）

**這個標記的用途是「回歸比對的斷點標記」**：CHANGELOG 的實際讀者包含自動化回歸流程（sha256 基線比對、逐像素 diff、黃金基線組），流程會拿這個標記決定「**這一版之前建立的基線還能不能直接拿來比對**」。範圍寫窄了，回歸驗證就會把預期內的改變誤報成回歸。

**判斷原則**：後續接手的人或流程**需不需要知道這件事，才不會把預期內的改變誤判成回歸**？需要 → 標。

**算「輸出變更」（要標）**

| 類別 | 涵蓋範圍 |
|---|---|
| **數值類** | 波形數值、計算結果、匯出檔案的位元組內容 |
| **版面／構圖類** | 可視列數、元素間距、canvas 尺寸。判準：**用「截圖／匯出圖片」功能存下來的成果，新舊版拿同一組設定重跑會長得不一樣**，就要標 |
| **同一操作序列得到不同結果** | 即使舊結果本身是 bug 造成的，仍要標。舊結果「合不合理」不是判準 —— 拿舊版建立的基線會不會失效才是 |

**不算（不標）**

- 純新增能力，既有操作的結果完全不變
- 只有互動方式增加（例如同一個目標多一種操作手勢），既有輸出不變
- 純文件、註解、說明頁

**與版號級別彼此獨立**：MAJOR／MINOR／PATCH 都可能帶 `⚠ 輸出變更`，也都可能不帶。R1 規範的是「修 bug 時的版號級別」，本節規範的是「什麼情況要掛這個標記」，兩者分開判定。

**R2｜一波重整以 MAJOR 開頭，波內的後續步驟依自身性質各自判定**

大改版不會一次做完。使用者被告知「這是 v2 重整」之後，同一波內的後續步驟不需要每步都 MAJOR（否則會出現 v2.0.0 → v3.0.0 → v4.0.0 這種荒謬編號）。

- 波的**第一版**用 MAJOR，宣告「要重新熟悉一次」。
- 波內後續：新增能力 → MINOR；修正／重構 → PATCH。
- 波內若移除既有入口，算在開頭那個 MAJOR 的宣告範圍內，不再另計。

#### 🔴 R2 補充：一波如何結束、如何開新波（2026-08-12 補）

原 R2 只寫了「波內怎麼判」，**沒有定義一波什麼時候結束**。這正是被繞過去的破口：只要主張「上一波已經結束了」，波內的第二次 MAJOR 就變成合法的，而這個主張沒有任何可檢驗的判準 —— 任何說詞都不可證偽。實際後果是同一個錯發生兩次（`pattern` v4.0.0、`wfg` v4.0.0，兩次都事後回溯更正）。

**明文規定：**

1. **一波不會自己結束。** 「主題跟上一波沒有交集」「上一波該收的都收完了」「分頁結構已經穩定」**都不是波次結束的判準**。這些都是撰稿者當下的感受，不是事實。
2. **開新波（＝進 MAJOR）必須有 Bruce 的明示裁示。** agent／任何撰稿者**不得自行判定某一波「已結束」**，也不得以任何書面說明自我授權開新波。
3. **判定順序**：先照 §1 判定表與 R1～R4 逐項判、取最高者。若結論落在 MAJOR，**停下來問 Bruce**，取得裁示後才編號。不確定就編較低的級別，並在 `判定依據：` 裡寫明取捨供覆核 —— **編低了下次可以補，編高了會永久留在 git commit 歷史裡改不掉。**
4. **「改動看起來很大」不是 MAJOR 的判準。** 一波可以走很遠：`wfg` 的 2.x 一路走到 `v2.97.475`，3.x 同樣可以走到 v3.9x。版號級別看的是「使用者原本會的操作還在不在、要不要重新確認結果」，不是工程規模或投入的心力。
5. **機械檢查**：`tools/version_bump_check.py` 於 pre-commit 攔截。MAJOR 沒有下述 `MAJOR 核准：` 欄位一律擋下（詳見 §4 C4）。

   閘門的正本在 **`tools/hooks/pre-commit`**（有進版控、可被審閱）；實際生效的是 `.git/hooks/pre-commit`，而 `.git/` 不進版控 —— **重新 clone 一份 repo，這道閘門預設不存在**。安裝／更新：

   ```
   ln -sf ../../tools/hooks/pre-commit .git/hooks/pre-commit
   ```

   用 symlink 而不是複製，正本改了就自動跟著改，不會出現兩份不同步的版本。此 hook 在三種情況會擋下 commit：版號判定不合規（rc=1）、**檢查腳本不見**、**檢查本身跑不起來（rc=2）**。後兩者原本都是「印一行警告然後放行」，等於刪掉守門員就能通過 —— 比填一個欄位還容易，2026-08-12 一併改為擋下。

**R3｜大功能分階段交付，每個「使用者真的多能做一件事」的階段各進一次 MINOR**

- 「存圖功能」分成 (a) 能存了、(b) 有預覽了、(c) 能拖曳了 → **三次 MINOR**，不是一次。
- 但「把存圖的按鈕從左邊移到右邊」不算 → PATCH。
- 判準：**這一版之後，使用者能做的事有沒有多一件？** 有 → MINOR，沒有 → PATCH。

**R4｜起始狀態／預設值改變（2026-08-04 補）**

改變「開啟時看到什麼」「某個選項的預設值」這類起始狀態：

- **不影響任何既有操作**（沒有功能被移除、沒有入口移位、原本會的操作照樣能做）→ **MINOR**
- 會**讓既有操作失效或移位** → **MAJOR**

理由：MAJOR 要防的是「使用者原本會的操作失效或找不到了」。單純換一個開啟時的預設畫面，不會讓任何既有操作失效，因此不觸發 MAJOR。

與 §2 案例 3（改 UI 版面）的分工：案例 3 判的是**控制項的位置**有沒有移動，R4 判的是**起始狀態的內容**有沒有改變。兩者的 MAJOR 門檻是同一句話 —— 使用者要不要重新找東西、原本會的操作還在不在。

## 2. 逐案例對照（Bruce 指定要逐一舉例）

| # | 案例 | 判定 | 理由 |
|---|---|---|---|
| 1 | **新增一個完整功能（例如 pattern 的遮罩）** | **MINOR** | 多了能做的事，既有畫面與操作全部不變。v1.9.0 這個編法是**對的** |
| 2 | **改一個 bug** | **PATCH** | 回到應有行為。若輸出會變，加 `⚠ 輸出變更`（R1） |
| 3 | **改 UI 版面、不動功能** | **看程度**：微調（間距、配色、文案、控制項位置小移）→ **PATCH**；重排到「原本的按鈕找不到了」→ **MAJOR** | 判準是使用者要不要重新找東西 |
| 4 | **重構資料結構、行為不變** | **PATCH** | 使用者完全無感。**風險高不等於版號要大** — 風險靠驗收條件管，不靠版號 |
| 5 | 新增一整組新畫面／新來源 | **MINOR** | 新增能力 |
| 6 | 移除一個既有功能 | **MAJOR** | 使用者原本會用的東西沒了。若在重整波內則併入開頭的 MAJOR（R2） |
| 7 | 既有計算公式修正（例如 calc 的 EM02 改 floor） | **PATCH ＋ `⚠ 輸出變更`** | 修正為應有行為，但舊報告的數字可能對不上 |
| 8 | 既有計算公式**主動改設計**（換一套演算法、換定義） | **MAJOR** | 使用者必須重新確認過去的結果 |
| 9 | 效能優化、行為不變 | **PATCH** | 無感 |
| 10 | 只是重新部署（Pages 卡住重推） | **不進版** | 見 §3 |
| 11 | 新增語言、i18n 文案補齊 | **PATCH** | 除非新增語言本身是宣傳點，那才 MINOR |
| 12 | 新增一個獨立的新分頁工具 | 該分頁 **v1.0.0**；首頁 `app` 進 **MINOR** | |

## 3. 不進版的情況

以下**不動版號**，避免版號變成 commit 計數器：

- 純部署重試（Pages build/deploy 失敗重推）
- 只改 `docs/`、`CHANGELOG.md`、註解
- `.bak` 檔清理、`.gitignore` 之類的雜務
- **同一個功能在同一天內的連續修補**：先做完再進一次版，不要每個 commit 進一次
- **純粹新增錨點 `id` 屬性**（不改任何顯示、計算、事件行為，僅供說明頁深層連結使用）（2026-08-08 起）
  - 判定方式：把新增的 `id` 屬性移除後，與前一版逐位元組比對必須完全相同。比對有差異就不適用本條，回到 §1 判定表判定。
  - 適用範圍：所有分頁的工具版號與首頁 `app` 總版號。
  - 生效方式：2026-08-08 之後的改動適用；此日之前已發布的版號不回溯調整（見 §5.5 修正記錄）。

> 這一條直接對應現況：全庫 979 個 commit 裡有大量 `chore: retry pages deploy…`、`redeploy: 觸發…`，那些都不該佔版號。

## 4. 一起訂的配套

**C1｜commit message 前綴統一為 `<工具>: `**
目前混用 `wfg v2.97.433:`、`fix(wfg):`、`ecbb640 v2.97.433:`、無前綴。統一成 `工具名: 描述`（進版時在描述裡帶版號），統計與追溯才可靠。

**C2｜版號只有一個來源**
`common/version.js` 已經是單一來源，維持。但**cache buster（各 html 的 `?v=` 字串）目前是手改的**，v1.9.0 的 `pattern.html` 用 `?v=20260801pat10` — 這個要跟版號綁在一起自動產生，否則會出現「版號進了但使用者拿到舊快取」。（已知歷史問題：commit `b674c6b` 就是在修 stale `?v=`。）

**C3｜CHANGELOG 每條開頭標版號與類型**
格式：`## <工具> vX.Y.Z — YYYY-MM-DD ｜ MAJOR/MINOR/PATCH`，輸出會變的加 `⚠ 輸出變更`。

**C4｜CHANGELOG 條目的具名欄位（2026-08-12 明文化）**

這三個欄位原本只存在於 `tools/version_bump_check.py` 的實作裡，文件從未寫過（本檔 grep「波次」＝ 0 筆）—— 工具與規則不同步，本身就是一個破口。此處補齊。

| 欄位 | 何時必填 | 性質 | 缺席的後果 |
|---|---|---|---|
| `判定依據：` | **每一次進版**（MAJOR／MINOR／PATCH 皆同） | **判斷**：`VERSIONING.md` 的哪一條、為什麼是這個級別 | pre-commit 擋下 |
| `MAJOR 核准：` | **只有 MAJOR**，一律必填（含該工具史上第一次 MAJOR） | 🔴 **外部事實**：Bruce 有沒有核准過這次 MAJOR | pre-commit 擋下 |
| `版號回溯核准：` | **只有版號倒退**（新版號小於前一版），一律必填 | 🔴 **外部事實**：Bruce 有沒有裁示回溯（見 §5） | pre-commit 擋下 |
| `波次宣告：` | 選填 | 純說明：本版與所屬那一波的關係 | **不擋**，也**不構成放行條件** |

兩個核准欄位的格式（整行、需可被機械解析：**核准人 ＋ `YYYY-MM-DD`，缺一不可，日期不得在未來**）：

```
MAJOR 核准：Bruce 2026-08-12
版號回溯核准：Bruce 2026-08-12
```

> 版號回溯經核准後**不等於免檢**：工具會改以「被回溯掉的那一版**之前**」為基準重新判定級別，`判定依據：`、宣告級別相符、`MAJOR 核准：` 等檢查一項都不會少。

> 🔴 **為什麼 MAJOR 的閘門是「核准」而不是「說明」**：閘門只有建立在**撰稿者自己認定不了的事實**上才有用。「這是不是新的一波」是判斷，agent 自己就能認定 → 當閘門必被繞過（`wfg` v4.0.0 就是填了 `波次宣告：` 一段作文後被放行的）。「Bruce 有沒有核准」是外部事實，agent 認定不了 → 可以當閘門。**填了而實際沒有取得核准，性質是說謊，不是判斷失準。**

## 5. ⚠️ 既有版號要不要回溯調整（提方案，**不自行執行**，待 Bruce 決定）

> 🔴 **2026-08-12 明示例外**：`wfg` **v4.0.0 → v3.6.0** 已回溯更正，依 **Bruce 2026-08-12 裁示**。
>
> 本節與 CHANGELOG 頂端公告的「歷史版號一律不回溯調整」仍是原則，本次是**經裁示的個案例外**，不構成先例 —— agent 不得自行決定回溯任何版號。
>
> **為什麼本次可行**（逐條對照下方方案 B 列出的代價）：
>
> | 方案 B 的代價 | 本次情況 |
> |---|---|
> | git commit message 裡的版號改不掉，造成永久矛盾 | **屬實，不迴避**：commit `6e32687` 會永遠寫著 v4.0.0。處理方式是**不改寫歷史、不 force push、不 rebase**，以一個新的更正 commit 完成，並在 CHANGELOG 該版〈版號更正紀錄〉寫明 |
> | tag / Release 對不上 | **不存在**：本 repo `git tag` 為空，沒有任何 tag 或 GitHub Release |
> | cache buster `?v=` 要重算 | 只有 `wfg.html` 兩處（`20260812wfg400` → `20260812wfg360`） |
> | 記憶中的版號、外部紀錄失效 | v4.0.0 上線僅數小時、未對外宣告 |
>
> 判斷原則：**回溯的成本可窮舉且已全部處理完 → 可行；否則不動歷史。**
>
> **機械檢查**：`tools/version_bump_check.py` 會把「新版號小於前一版」判為違規，唯一出口是該 CHANGELOG 條目寫上 `版號回溯核准：<人名> <YYYY-MM-DD>`（見 §4 C4）。留這道窄門而不是擋死，是因為擋死的實際後果是 `git commit --no-verify` —— 那等於整道閘門在最需要它的時候被整個關掉。

### 方案 A：不動歷史，從下一版起套新規則

- **代價**：零。
- **缺點**：`wfg v2.97.475` 這個號碼永遠是個怪東西；新舊規則的分界看不出來。

### 方案 B：全部重編歷史版號

- **代價（都是真的會痛的）**：
  1. `CHANGELOG.md` 全部要重寫，而且**git commit message 裡的版號改不掉**（改歷史 commit 等於重寫整個 repo 歷史），會造成 CHANGELOG 說 v1.4.0、commit 說 v1.7.0 的永久矛盾。
  2. 各 html 的 cache buster `?v=` 字串要全部重算。
  3. **Bruce 記憶中的版號全部失效** — 「那個 bug 是 v2.97.450 修的」這種對話紀錄、vault journal、Notion 記錄全部對不上。
  4. 使用者（同事）如果回報「我用的是 v2.97.4xx」，也對不上。
- **我不建議。** 收益只有「好看」，代價是永久性的追溯困難。

### 方案 C（我的建議）：不動歷史，但用一次明顯的跳版標記分界

- 在 `CHANGELOG.md` 頂端加一則「版本規則變更公告」，寫明生效日與新規則連結。
- 下一次進版時**各分頁跨一個看得出來的界線**，例如：
  - `wfg` v2.97.475 → **v3.0.0**（它的 patch 號早就爆掉，正好藉這次歸零）
  - `pattern` v1.9.0 → **v2.0.0**（本來就要做 v2 重整，天然吻合）
  - `isp` / `aux` / `calc` / `rxtx` → 下次進版時各自往 MINOR 或 MAJOR 跨一格，並在 CHANGELOG 標註「此版起套用新規則」
- **代價**：只有一次跳版，歷史完全不動，且分界點清楚可查。
