## 🔴 §0 不可違反的硬規格：像素等級 Pattern 的完整性

> **這一節優先於本文件所有其他設計。任何與它衝突的設計一律作廢重做。**

### Bruce 的原話（逐字）

> 「在 LCD Pattern 測試這個行業，最重要的一點是：如果 Pattern 設計的是像 Pixel On-Off 或 Subpixel On-Off 這種像素等級、重複性的 Pattern，**絕對不能因為解析度改變，而把這些像素等級的 Pixel 排列給改變**。
> 這點是要非常非常注意的。」

### 這條規格的四項硬性要求

**H1｜存圖一律以目標解析度「原生重畫」，禁止任何重取樣路徑**

必須走**同一支逐像素產生器**，用目標解析度當 `W/H` 直接產生每一個像素。

**明文禁止**（以下任一出現即為違規）：

| 禁止的做法 | 為什麼致命 |
|---|---|
| 畫小張再放大 | 插值把 1px 線變成 2px 灰邊，Pixel On-Off 直接糊掉 |
| 畫大張再縮小 | 相鄰的亮暗像素被平均成灰色，紋路整個消失 |
| `drawImage` 做任何縮放 | 同上，且 `imageSmoothingEnabled=false` 也只是變成最近鄰取樣，**仍會改變週期與相位** |
| CSS `transform: scale()` 後截圖 | 同上，且引入 dPR 這個不可控變數 |
| 先渲染到螢幕 canvas 再讀出來當輸出 | 螢幕 canvas 的尺寸受 dPR／視窗影響，不是目標尺寸 |

**唯一允許的路徑**：
```js
var cv = document.createElement('canvas');
cv.width = 目標W; cv.height = 目標H;          // ← 直接就是目標裝置像素
var ctx = cv.getContext('2d', { alpha:false });
ctx.imageSmoothingEnabled = false;
pgDrawPattern(ctx, 目標W, 目標H);             // ← 同一支引擎，逐像素直寫
// 或 subpixel 模式：pgTileLevels(ctx, 目標W, 目標H)
cv.toBlob(cb, 'image/png');                   // PNG 無損
```

> 好消息：**現行引擎已經滿足這個要求**。`pgDrawPattern`（行 1258）的 `W/H` 是純參數，`pgPixels`（行 1203）用 `Uint32Array` 逐像素直寫再 `putImageData`，全程無縮放無內插。§4-1-1 已實測 2560×1440 可直接產生。**所以要做的是「不要破壞它」，不是「去實作它」。**

**H2｜相位與起點不可位移**

同一個畫面在任何解析度下：

- 第 `(0,0)` 個裝置像素的明暗**必須相同**
- 週期規則**必須相同**（例如 `Skip 1 Dot 1V 1H` 恆為 `(x + y) mod 2`，不因 W/H 改變）

> ⚠️ **已知例外，必須明確標示而非默默接受**：`Skip 1 Dot 1V 2H`、`Skip 2 Dot 2V 2H`、`Skip 2 Dot 2V (1+2)H` 這三張的相位公式**本來就含 H**（行 1308／1312／1314：`m4(x - 2y + 2H - inv)` 等）——這是**原程式的既有行為**，不是我們引入的缺陷。
> 處理方式：**不改公式**（改了就不是原程式的畫面了），但在存圖 UI 上針對這三張顯示 `此畫面的相位依畫面高度決定，不同輸出高度的相位會不同`，讓使用者知道。**其餘所有像素等級畫面必須通過 H2。**

**H3｜預覽不可騙人**

- 目標**大於**基準時，必須是 **1:1 平移檢視**（手爪拖曳），**不可以縮小塞進視窗**。縮小後看到的紋路根本不是存出去的東西。
- 若在「符合視窗」模式下必然發生縮放，該模式**必須明確標示**：
  `⚠ 此檢視經過縮放，紋路僅供構圖參考，非實際輸出`
- 這行警語**不可以只在說明文字裡**，要**貼在預覽畫面上**（縮放模式時常駐）。

**H4｜遮罩 pad 的幾何佔比問題與本節無關，不得混為一談**

先前量到「pad 是絕對像素，露出佔比隨尺寸變 18.77% / 19.77% / 22.97%」（§8 #4）——那是**遮罩露出區的幾何佔比**問題。

**像素排列本身在各尺寸下必須完全一致**，這是兩件不同的事：
- pad 影響的是「哪一段被蓋住」
- H1/H2 管的是「沒被蓋住的那一段，裡面的像素排列對不對」

**遮罩開著時，露出區內的像素排列仍必須通過 H1/H2 的全部檢查。**

### 驗收條件（v2.2.x 存圖的**每一版**都要過，不是只做一次）

**受測畫面**（像素等級、重複性）：

| 畫面 | 應有的週期規則 |
|---|---|
| Pixel On-Off ≡ `Skip 1 Dot ▸ 1V 1H` | `(x + y) mod 2` |
| Subpixel On-Off ≡ `Skip SubPixel` | `(x + y) mod 2`，兩色為 G / Magenta |
| `Skip 1 Dot ▸ 1V 2H` | 含 H（H2 例外，改驗「同一 H 下規則成立」） |
| `Skip 2 Dot ▸ 2V 1H` | `(x + (y>>1)) mod 2` |
| `Skip 2 Dot ▸ 2V 2H` | 含 H（同上例外處理） |
| `Skip 2 Dot ▸ 2V (1+2)H` | 含 H（同上例外處理） |
| `Vertical Line ▸ Sub Line` | `x mod 2`，兩色為 G / Magenta |
| `Horizontal Line ▸ 1 line` | `y mod 2` |
| `Vertical Line ▸ 1 line` | `x mod 2` |

**測試矩陣**：上述每一張 × **1920×1080 / 2560×1440 / 3840×2160** → 存出**實際 PNG 檔案**

**檢查項目（三項全過才算通過）**：

1. **解碼 PNG 後**（不是讀 canvas，要讀實際存出來的檔案），取左上角 **16×16 區塊**的明暗矩陣 → **三個解析度必須完全相同**
2. **全圖**套用該畫面應有的週期規則逐像素驗證 → **不符數必須為 0**
3. 上述第 2 項在**三個解析度下都要是 0**

**額外**：遮罩開啟的情況也要各跑一次，驗證露出區內同樣是 0 不符。

**回報要求**：附上實際數字（例如 `3840×2160 Skip 1 Dot 1V1H：檢查 8,294,400 px，規則不符 0 px`）。
**不接受**「看起來一樣」、不接受抽樣、不接受只比對雜湊（雜湊只能證明兩張圖相同，不能證明**排列規則正確**）。

### 1-3 到底哪裡混亂？（具體指出）

> 這一節是「診斷」，不是「很多東西」這種空話。每一條都指得到元素。

**M1｜同一件事有兩個以上入口，而且行為不同**

- **顏色**：編輯器的 R/G/B 標題 +（0–255 灰階）是一組；畫面參數的「顏色 1–8」是另一組（`PG_CNAME`，含 White/Black/Cyan/Magenta/Yellow）。兩者在同一張卡片內上下相鄰，但**互斥**——動了上面那組會 `pgLeavePattern()` 把下面整區收掉（行 834、841）。
- **灰階**：`pg-level-num/range`（380）與 `pg-pat-lv-num/range`（433）長得一模一樣、隔了 40 行、只有一個當下有效。
- **快速樣式**：主頁 9 顆（402）＋全畫面面板 9 顆（`pgBuildFsQuick`，2722），共 18 個按鈕做 9 件事。
- **選單**：主頁下拉鈕（416）、全畫面面板鈕（618）、全畫面右鍵（2495），三個入口共用一棵樹——這一項是**好的**設計，應保留。

**M2｜「模式」這件事沒有任何顯性的視覺表達**

`pgMode` 決定了畫面怎麼畫、編輯器能不能動、哪些控制項有效，但畫面上唯一的線索是：`pg-cur-bar` 有沒有出現、以及編輯器有沒有變灰（`.pg-grid-wrap.na`，行 242 只是 `opacity:.38`）。使用者不會知道「我現在按這顆會不會把剛才選的畫面弄丟」。

**M3｜卡片標題與內容不符**

卡片 B 叫「Sub-pixel 編輯（4 px × 4 列）」，但它裡面同時裝了：34 項測試畫面選單、Cross Talk 的 8 個參數、Response Time 的 6 個參數。**測試畫面選單是這個工具現在最主要的功能，卻藏在一張叫「Sub-pixel 編輯」的卡片下半段。**

**M4｜控制項與它影響的東西距離太遠**

預覽 canvas 在卡片 D（582），但影響預覽的控制項散在卡片 B（灰階、顏色、變體）與卡片 C（遮罩全部）。手機上要捲動 2–3 個螢幕高度才能一邊改一邊看。

**M5｜pattern 專屬參數用「顯示／隱藏」堆疊，撐不住擴充**

`pgSyncPatternUI()`（2225）用 4 個 `show()` 開關 `pg-pat-checker` / `pg-pat-ct` / `pg-pat-rt` / `pg-pat-xy`，另外還有一條寫死的排除清單決定灰階框要不要出現：

```js
show('pg-pat-lv-box', pgPat.id !== 'checker' && pgPat.id !== 'smpte' && pgPat.id !== 'colortest' &&
                      pgPat.id !== 'crosstalk' && pgPat.id !== 'resptime' && pgPat.id !== 'xy');   // 行 2245
```

每加一張新畫面就要回來改這條字串比較。**這是加新來源時第一個會爆的地方。**

**M6｜遮罩獨立成一張卡，但它其實是「輸出層」**

遮罩對 subpixel 與 pattern 兩種模式都有效，卻放在兩者之間，位置上暗示它跟 pattern 同層。而且它有 12 個控制項，是全頁最重的一張卡，卻是最少用的功能。

**M7｜螢幕資訊卡佔了整個第一屏，但它是唯讀的**

手機開啟後第一眼看到的是 8 個唯讀數字 + 3 段說明文字，要捲過去才會看到能操作的東西。

## 二、需求 1：快速樣式怎麼簡化

### 2-1 先驗證 Bruce 的假設是否成立

Bruce 說：「階層式選單已經可以取代這些功能。」

**驗證方法**：本機 http server 載入 v1.9.0 → 把 overlay 開起來（`classList.add('on')`）讓 `pgRenderFill()` 畫到 `#pg-fs-canvas`（3810 × 1916 裝置像素 = 7,299,960 px）→ 對整張 canvas 的 `Uint32Array` 做 FNV-1a 逐像素雜湊 → 比對兩邊。**不是抽樣，是整張逐像素。**

**結果：9 顆全部可以用選單畫出逐像素相同的結果。**

|---|---|---|---|---|
| 1 | L0 | `Gray Level` | 灰階 → 0（預設 127） | ✅ SAME `9acb1425` |
| 2 | L255 | `Gray Level` | 灰階 → 255 | ✅ SAME `e03ef8ad` |

### 2-2 但「可取代」不等於「該刪」——三個實質差異

**差異 1：操作步數。** 快速樣式是 1 下；選單等價路徑是 3–5 下（開選單 → 進子選單 → 點畫面 → 調灰階 → 有時還要按 Space）。這 9 顆全部都要「灰階調到 0 或 255」，而選單畫面進入時的預設灰階是 127（`PG_DEF`，行 1157–1172）。

**差異 2：模式不同，後續能做的事不同。**
- 按快速樣式 → 停在 `subpixel` 模式 → **4×4 格子每一格都還能手動改**。這是「載入一個起點再手改」。
- 走選單 → 進 `pattern` 模式 → 編輯器變成唯讀反推顯示，一動就 `pgLeavePattern()` 跳回 subpixel（行 834）。

**差異 3：這 9 顆是 Bruce 先前明確要求保留的。** 所以「簡化」的目標是**減少視覺重量與重複**，不是清空功能。

### 2-3 三種簡化程度 — ✅ 已裁決（最終方案見 §7 D1）

> **裁決結果**：都不是這三個原案，Bruce 訂的是「**收進選單，只留一排捷徑，捷徑是選單的薄殼、共用同一份資料來源**」——比方案乙更進一步，從結構上杜絕兩條路徑分岔。留下的 5 顆與方案乙相同。下面三案保留作為推導紀錄。

**方案 甲｜就地瘦身（最保守）**

- 全畫面面板那份 9 顆改成「最近用過的 3 顆」，其餘進選單。
- 改動量：CSS + 20 行 JS。風險極低。

**方案 乙｜降為「起手式」，數量砍到 5（建議）**
- 保留 **L0 / L255 / R255 / G255 / B255**（純色，1 下到位，選單要 2–3 下，價值最高）。
- 移除 **Pixel on/off / V 1 Line / H 1 Line / Subpixel On/Off**（4 顆），因為它們在選單裡是**獨立的正式畫面**（`Skip 1 Dot ▸ 1V 1H`、`Vertical Line ▸ 1 line`、`Horizontal Line ▸ 1 line`、`Skip SubPixel`），保留兩份等於同一張畫面有兩個名字。
- 這 5 顆改名為「**起始樣式**」，並在旁邊註明「載入後可繼續手動編輯 4×4」——把它與選單的語意差異講白。

**方案 丙｜完全合併（最激進）**

**我的建議：方案 乙。** 理由：它砍掉的 4 顆是**確定重複**的（選單有同名正式畫面），保留的 5 顆是**確定不重複**的（選單裡沒有「一鍵純色」，`Gray Level` 預設 127 且要另外選色）。這條界線有客觀依據，不是憑感覺挑數量。

### 3-3 資料結構草案（重點：加新來源不動任何 UI 程式碼）

現在的問題是：畫面的「行為」散在 6 個地方，加一張新畫面要改 6 處。

| 目前散落處 | 行 | 內容 |
|---|---|---|
| `PG_MENU` | 1115 | 選單樹 |
| `PG_GROUPS` | 1147 | 變體循環群組 |

    def:       { colorIdx: 3, level: 127 },   // 取代 PG_DEF
    keyGroup:  'level',                       // 取代 pgKeyGroup() 的 regex
    infoMode:  200,                           // 取代 PG_MODE
    variants:  'gray',                        // 取代 PG_GROUPS：同一個 variants 值 = 同一個循環群

| 預設值 | `PG_DEF` | `def` |
| 鍵盤 | `pgKeyGroup()` 的 regex 串 | `keyGroup` |

### 3-4 三個附帶設計問題

**Q1：只有一個來源時要不要多一層？**
建議 **要**，但**自動展開**：`PG_SOURCES.length === 1` 時，選單根層直接顯示該來源的內容，不多包一層；長度 ≥ 2 時才出現來源層。這樣現在的操作步數完全不變，加了第二個來源自動變兩層。判斷寫在建樹函式裡一行，不影響資料結構。

**Q2：常用畫面要不要捷徑？**
建議 **要**，做成「最近使用」而不是「我的最愛」——選單頂端固定放最近選過的 3–5 個（含來源前綴），存 `localStorage`。理由：FAE 一次量測通常反覆切同幾張，「最近使用」零維護成本，「我的最愛」要使用者自己管理。

**Q3：搜尋要不要？**
**現階段不要。** 34 項、三個入口都是滑鼠／觸控操作，搜尋框要打字，在全畫面右鍵選單裡尤其突兀。等來源數 ≥ 3 且總畫面數 > 80 再回頭做。

需求 2 要「先選來源」，但專案規則是公開面不得出現廠商／客戶名稱。

**裁決：採 B。** 命名規則、候選名（建議 `Skip／LUMINACE 組`）與延續方式見 §7 D2。廠商名一個字都不出現 —— 包含顯示文字、程式碼識別字、註解、CHANGELOG、commit message、檔名。內部識別字用 `set_skip_lum` 之類的語意代號，**不用 `lcdtest2010` 這種序號**。

## 四、需求 3：存圖系統

這一項最複雜，拆成 (a) 尺寸、(b) 預覽提示、(c) 拖曳三段。

### 4-1 (a) 自訂解析度存圖

#### 4-1-1 好消息：繪圖引擎本身已經是完全參數化的

`pgDrawPattern(ctx, W, H, stateOverride)`（行 1258）的 W/H 是純參數，沒有讀任何全域尺寸。

**實測**（把 `#pg-fs` 的 CSS 尺寸改掉再 `pgRenderFill()`，dPR = 2）：

| overlay CSS | canvas 實際 | `pgTargetSize()` | SMPTE 取樣（左上 / 1/16W,1/4H / 正中） |
|---|---|---|---|
| 1905 × 958 | 3810 × 1916 | 3810 × 1916 | `104,104,104` / `104,104,104` / `0,192,0` |
| 1280 × 720 | **2560 × 1440** | 2560 × 1440 | `104,104,104` / `104,104,104` / `0,192,0` |
| 640 × 360 | 1280 × 720 | 1280 × 720 | `104,104,104` / `104,104,104` / `0,192,0` |

→ **2560 × 1440 已經畫得出來，而且相對幾何完全一致。**

所以 (a) 的技術路徑很短：

```js
function pgRenderToSize(W, H, opts){
  var cv = document.createElement('canvas');
  cv.width = W; cv.height = H;
  var ctx = cv.getContext('2d', { alpha: false });
  ctx.imageSmoothingEnabled = false;
  if (pgMode === 'pattern') pgDrawPattern(ctx, W, H);
  else                      pgTileLevels(ctx, W, H);     // 4×4 平鋪：與尺寸無關
  if (opts.mask) pgApplyMask(ctx, W, H);                 // 見 §7 決策 D3
  if (opts.info) pgDrawInfoOnCanvas(ctx, W, H, opts);    // 見 §7 決策 D4（新寫）
  return cv;
}
```

**唯一必須先改的既有結構**：`pgTargetSize()`（1632）目前寫死讀 `#pg-fs`。要讓存圖用另一個尺寸，得把「目前作用中的目標尺寸」變成可覆寫的：

```js
var pgSizeOverride = null;
function pgTargetSize(){
  if (pgSizeOverride) return pgSizeOverride;      // 存圖／預覽時暫時指定
  var sz = pgFillCssSize(), dpr = window.devicePixelRatio || 1;
  return { W: Math.max(1, Math.round(sz.w*dpr)), H: Math.max(1, Math.round(sz.h*dpr)) };
}
```

這一改會連帶影響 5 個呼叫點：`pgDetectPeriod`（1680）、`pgGeomKey`（1702）、`pgInfoText`（1892）、`pgSelectPattern` 的 Cross Talk 進入點（1935）、`pgHandlePatternKey` 的 crosstalk/xy 分支（2039、2074）。**必須用 try/finally 包住，確保存圖結束一定還原**，否則全畫面的鍵盤操作會用到錯的尺寸。

| 11 | `checker` 格寬 | 1413–1416 | `F(W*i/n)` | **實測** n=256：W=3810 → 前幾格 `14,15,15,15…`（不均）；W=2560 → 全部 `10`（均勻） | 這其實是**自訂解析度的好處**，應在 UI 提示「此尺寸下 Checker 格寬均勻／不均勻」 |

另外一項與尺寸有關但屬於 pattern 本身語意的：**Skip 系列相位含 H**（行 1308、1312、1314：`m4(x - 2y + 2H - inv)` 等）。換高度會換相位——這是原程式行為，存圖時應如實反映，不需要「修」，但值得在存圖預覽上提示「此畫面的相位隨高度改變」。

#### 4-1-3 存檔格式 — ✅ 已裁決：**PNG 與 BMP 都做**（D7）

##### 格式本身不是風險來源

**PNG 是無損格式**（DEFLATE 壓縮），解碼回來的像素值與編碼進去的位元**完全相同**，保真度與 BMP 沒有差別。BMP 只是不壓縮，代價是檔案大很多。

| 格式 | 3840×2160 檔案大小 | 保真度 |
|---|---|---|
| PNG | 視內容而定（棋盤類壓縮率高，實測 512×512 棋盤＋漸層只要 8,252 bytes） | 無損 |
| BMP 24-bit | **約 24.9 MB**（`54 + 3840×3×2160`，寬度是 4 的倍數所以無 padding） | 無損 |

**不提供 JPEG／WebP 有損選項**：測試畫面全是硬邊界與精確灰階，JPEG 會在邊界產生 ringing、把 L127 變成 L126/L128，直接毀掉這個工具的用途。

##### 🔴 真正的風險在產生路徑，共四條

**風險 1：Alpha 預乘 — 實測確認風險真實存在，但我們的路徑不會踩到**

canvas 預設帶 alpha，瀏覽器內部可能以**預乘 alpha** 儲存，半透明像素反算回來會有捨入誤差。

實測（Chrome，512×512 全 256 階灰＋像素棋盤）：

| 路徑 | 結果 |
|---|---|
| `{alpha:false}` ＋ `putImageData`，每像素 alpha=255 | PNG 往返 **差異 0 / 262,144** ✅ |
| `{alpha:true}` ＋ `putImageData`，每像素 alpha=255 | PNG 往返 **差異 0 / 262,144** ✅（但檔案大 32%：10,903 vs 8,252 bytes） |
| `{alpha:true}` ＋ `putImageData`，alpha=128 | PNG 往返 **差異 0 / 262,144**（`putImageData` 是直寫路徑，不經預乘） |
| **`{alpha:true}` ＋ `ctx.fillStyle='rgba(...)'` ＋ `fillRect`** | 🔴 **256 級 alpha 中有 196 個反預乘後 RGB 偏離原值**。例：`rgba(200,100,50,α)` 在 α=1/255 時讀回變成 `255,0,0`；α=3/255 時變成 `170,85,85` |

**結論**：風險存在於 **`rgba()` 半透明繪圖路徑**，不存在於 `putImageData` 直寫路徑。
我們的引擎：`pgPixels`（行 1203）走 `putImageData` 直寫、`box()`（行 1261）用**不透明** `rgb()` —— **所以碰巧安全**。

> ⚠️ 「碰巧安全」不可接受。**必須用 `{alpha: false}` 把它變成結構上安全**，這樣即使日後有人加了半透明繪製也不會失真（`alpha:false` 的 context 每像素 alpha 恆為 255）。順帶檔案還小 32%。

**風險 2：色彩管理 / ICC profile**
像素數值不會被改，但**下游看圖軟體若做色彩轉換就會偏**。
- 實測：`getContextAttributes().colorSpace` 為 `srgb`（Chrome 預設）。建立 context 時**明確指定** `colorSpace: 'srgb'`，不要依賴預設值。
- UI 必須註明：`此圖為 sRGB 原始像素值，下游檢視工具請關閉色彩管理／色彩轉換`。

**風險 3：位元深度**
canvas 每通道 8 bit ＝ L0～L255，PNG 8-bit/channel、BMP 24-bit 都完整承接。實測全 256 階灰往返 0 差異 → **確認無誤，無須額外處理**。

**風險 4：縮放** —— 見 **§0 H1**，最致命的一條，已列為硬規格。

##### 🔴 D7 核心要求：每次存圖都自動跑一次機械證明

**存檔後把檔案解碼回來，跟來源 canvas 逐像素比對，差異數必須為 0，並把這個數字顯示在畫面上。**

```js
// 存檔流程的最後一步，PNG 與 BMP 兩種格式都要跑
async function verifyRoundTrip(blob, srcCtx, W, H){
  var bmp = await createImageBitmap(blob);
  var c2 = document.createElement('canvas'); c2.width = W; c2.height = H;
  var x2 = c2.getContext('2d', { alpha:false, colorSpace:'srgb' });
  x2.imageSmoothingEnabled = false;
  x2.drawImage(bmp, 0, 0);
  var a = new Uint32Array(srcCtx.getImageData(0,0,W,H).data.buffer);
  var b = new Uint32Array(x2.getImageData(0,0,W,H).data.buffer);
  var n = 0; for (var i=0;i<a.length;i++) if (a[i] !== b[i]) n++;
  return n;                       // ← 必須是 0，且必須顯示給使用者看
}
```

UI 表現：存檔完成後顯示 `✅ 已驗證：8,294,400 px 逐像素比對，差異 0`；**若不為 0 則以紅色顯示差異數並保留檔案**（不要偷偷丟掉，那反而讓人無從追查）。

> 這條的意義：讓「有沒有偏差」變成**每次存圖都自動驗一次的事實**，而不是靠我們口頭保證。

##### BMP 編碼器（要自己寫，瀏覽器 canvas 不原生輸出 BMP）

三個容易錯的地方，**已寫出原型並用上面那道機械證明驗過**：

| 坑 | 正確做法 |
|---|---|
| **色彩排列** | 24-bit BMP 是 **BGR**，不是 RGB。寫入時 `u8[o]=data[i+2]; u8[o+1]=data[i+1]; u8[o+2]=data[i]` |
| **每列 4-byte 對齊** | `pad = (4 - (W*3) % 4) % 4`，每列尾端補 `pad` 個 0。**寬度不是 4 的倍數時才會踩到**，所以測試一定要用非 4 倍數的寬 |
| **列順序** | `BITMAPINFOHEADER` 的 height 為**正數時是 bottom-up**（最後一列先寫）。寫成 top-down 的話圖會上下顛倒 |

**原型實測結果**（刻意選 **513×257**，寬非 4 倍數 → `pad = 1`，逼出 padding 路徑）：

| 檢查項 | 結果 |
|---|---|
| 檔案大小 | 395,834 bytes ＝ 理論值 `54 + (513×3 + 1) × 257` ✅ |
| 解碼後尺寸 | 513 × 257 ✅（沒有上下顛倒、沒有錯位） |
| **逐像素比對** | **差異 0 / 131,841** ✅ |

> 這比「讀 spec 保證我寫對了」硬得多 —— 如果 BGR 寫反、padding 少算、或列順序錯，比對數字不可能是 0。

##### 檔名與多尺寸匯出

- **檔名規則**（可在 UI 覆寫）：
  `pattern_<畫面id>_<顏色>_L<灰階><_inv><_mask>_<W>x<H>.<png|bmp>`
  例：`pattern_skip1_1v1h_White_L255_inv_2560x1440.png`
  遮罩開啟時加 `_mask`；subpixel 模式用 `subpixel_<4×4 的 12 個值雜湊前 6 碼>`。
- **一次匯出多個尺寸：做。** 成本極低（同一支 `pgRenderToSize` 迴圈跑幾次）。尺寸清單可勾選（預設 1920×1080 / 2560×1440 / 3840×2160 / 目前螢幕），逐檔 `download`（不引入 zip 函式庫）。
  ⚠️ **批次路徑是最容易偷偷引入「畫一張再縮放成多張」的地方** —— 每個尺寸都必須各自走一次 `pgRenderToSize`，且各自跑一次機械證明。

### 4-2 (b) 預覽與尺寸視覺提示

需求原文：「需要有明確的視覺提示，讓使用者一眼就能確定目前的圖片尺寸是剛好符合螢幕解析度，還是偏大或偏小。」

**設計原則**：一眼能判斷的是**形狀與位置關係**，不是數字。所以主要提示用幾何，數字只做佐證。

**建議設計：套疊比例框（overlay frame）**

```
┌─────────────────────────────────────────────┐
│ 目標 2560 × 1440              放大率 67%  ↕ │
│  ┌───────────────────────────────────────┐  │
│  │  ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐        │  │  ← 虛線白框 = 實機螢幕 3810×1916
│  │  │                           │        │  │     （永遠畫在同一個比例基準上）
│  │  │      〔pattern 內容〕      │        │  │
│  │  │                           │        │  │  ← 實線彩框 = 目標尺寸
│  │  └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘        │  │
│  └───────────────────────────────────────┘  │
│  ▸ 目標比螢幕小：寬 −1250 px、高 −476 px    │
└─────────────────────────────────────────────┘
```

三種狀態的視覺語言（三者要能在不看文字的情況下區分）：

| 狀態 | 邊框 | 底色標記 | 一行文字 |
|---|---|---|---|
| **剛好等於螢幕** | 兩框完全重合，改畫**單一綠色實線** | 綠 | `= 螢幕原生 3810 × 1916，1:1` |
| **目標大於螢幕** | 彩框在虛線框**外側**，四邊露出 | 琥珀 | `比螢幕大：寬 +650、高 +524` |
| **目標小於螢幕** | 彩框在虛線框**內側**，四周留白 | 藍 | `比螢幕小：寬 −1250、高 −476` |

**為什麼這樣最直觀**：使用者要判斷的其實是「這張圖放到面板上會不會剛好」——那是一個**包含關係**問題（內／外／重合），套疊框把它直接畫成包含關係，不需要心算兩組數字誰大誰小。顏色只是輔助強化，色盲情況下靠框的內外位置仍可判讀。

**補充提示（次要，放在同一區）**：
- 長寬比不同時額外標一行（例如目標 16:9、螢幕 1.988:1 → 提示「長寬比與螢幕不同」）。
- `checker` 類畫面在此尺寸下格寬是否均勻（依 §4-1-2 #11 實測可直接算出來）。
- 目標尺寸非 dPR 整數倍時提示「螢幕上看到的預覽會經過縮放，非 1:1」。

**預覽本身怎麼畫**：用 `pgRenderToSize(W, H)` 產生離屏 canvas，再以 `drawImage` 縮到預覽區。**縮小顯示時務必開 `imageSmoothingEnabled = true`**（與全畫面相反）——否則 1px 線條的畫面在縮圖上會整條消失，看起來像空白。

> 🔴 **這裡是 §0 H3 的正面戰場，必須非常小心。**
> 「符合視窗」模式**必然縮放**，而縮放後看到的紋路**不是**存出去的東西 —— Pixel On-Off 縮小之後會變成一片灰或摩爾紋。所以：
> 1. 該模式**必須常駐**顯示 `⚠ 此檢視經過縮放，紋路僅供構圖參考，非實際輸出`，且**貼在預覽畫面上**，不是藏在說明文字裡。
> 2. **這條縮放路徑只准用於螢幕顯示，絕對不可用於產生輸出檔案。** `pgRenderToSize()` 的離屏 canvas 才是輸出來源，`drawImage` 縮出來的那張只是給眼睛看的。實作時兩者要在程式碼裡明確分開命名（例如 `exportCanvas` vs `previewCanvas`），不要讓後人接手時搞混。
> 3. 想看真實紋路 → 切「1:1 實際像素」模式或按「⛶ 全畫面預覽」，那兩條路徑不縮放。

### 4-3 (c) 滑鼠左鍵拖曳 — ✅ 已裁決：平移檢視

**Bruce 指定的互動規格（逐字）：**

> 「如果解析度大於目前螢幕的解析度，可以在四周用呼吸燈式的紅框（慢慢變亮、慢慢變暗）來警告使用者，提示這個解析度已經大於目前螢幕的解析度。
> 在這個時候，如果按住滑鼠左鍵不放，遊標會變成一個手爪的形式，代表我可以上下左右拖曳這個畫面（因為畫面本身的解析度已經大於目前螢幕的解析度）。所以如果解析度小於螢幕本身的解析度，其實就讓它置中顯示就好，四周都留出黑框（黑色的部分）。」

#### 三態的完整規格

| 狀態 | 視覺 | 游標 | 拖曳 |
|---|---|---|---|
| **目標 > 基準** | 四周**呼吸燈紅框**：`box-shadow: inset 0 0 0 3px rgba(239,68,68,α)`，α 在 `0.25 ↔ 1.0` 之間以 **3 秒一個週期**用 `ease-in-out` 來回（**不是閃爍**，用 CSS `@keyframes` + `animation-direction: alternate`；同時加 `@media (prefers-reduced-motion: reduce)` 降級為靜態紅框） | 靜止 `grab`、按住 `grabbing` | ✅ 上下左右 |
| **目標 < 基準** | **置中顯示，四周留黑邊**（`#000`）。黑邊本身即是「比較小」的視覺訊號 | `default` | ❌ |
| **目標 = 基準** | **綠色實線框一次淡入（0.4 s）後停住不再變化**。與紅框的區別是「靜止 vs 持續呼吸」＋「綠 vs 紅」，兩個維度都不同，即使色覺差異也分得出來 | `default` | ❌ |

#### ⚠️ 追加語意（必須在 UI 上表達清楚）

**拖曳只改變「螢幕上看哪一塊」，永遠不影響存檔內容。存出去的一律是完整的目標解析度。**

表達方式：拖曳中在畫面角落顯示 `檢視位置 x, y ／ 存檔內容不受影響`；存圖按鈕旁固定一行 `輸出：2560 × 1440 完整畫面`。**不要**用任何暗示「可以裁切」的字眼。

| 解讀 | 拖曳的意思 | 什麼時候有用 | 實作 |
|---|---|---|---|
| **甲：平移檢視（pan）** | 預覽區當成一個視窗，拖曳移動「看的位置」，圖本身不變 | 目標尺寸 > 預覽區、想 1:1 檢查局部細節（例如看 Skip 系列的相位）時**很有用** | 只改預覽的 `drawImage` 來源矩形，不動任何 pattern 狀態；配合滾輪縮放 |
| **乙：移動圖在畫布中的位置（offset）** | 目標畫布固定 W×H，pattern 內容在裡面平移，露出的邊補背景色 | 想把某個特徵（例如 Cross Talk 內框、XY 準星）挪到指定位置再存圖 | 要在 `pgRenderToSize` 加 `offsetX/offsetY`，並決定露出區補什麼色 |
| **丙：拖曳調整畫面內的可拖物件** | 拖 Cross Talk 內框、拖 XY 準星、拖遮罩露出區邊界 | 這三個東西目前只能用鍵盤或數字框調，拖曳會**大幅好用** | 各畫面要各自定義 hit-test；工作量最大 |

> 上表保留作為紀錄。**已裁決採「甲：平移檢視」**；「丙：拖曳畫面內物件（Cross Talk 內框／XY 準星／遮罩邊界）」價值仍高但範圍大，獨立成 v2.5.0 另行規劃，與甲不衝突（甲在預覽、丙在全畫面）。「乙」不採用。

#### ⚠️ 呼吸燈紅框 與 套疊比例框 會不會互相干擾？我的判斷：**不衝突，但必須分成兩個檢視模式，不能同時作用在同一個畫布上**

原因是兩者**預設的縮放前提相反**：

- **套疊比例框**（§4-2）成立的前提是「整張目標圖縮到看得完」——只有看得到目標框的四個邊，才能用「在虛線框內側／外側」判斷大小。
- **呼吸燈紅框 + 拖曳**成立的前提是「看不完，有東西在畫面外」——如果整張都看得完，就沒有東西可以拖，紅框也失去意義。

所以解法是**一個明確的檢視模式切換**，而不是把兩個效果疊在一起：

```
預覽區上方：檢視  [ 符合視窗 ]  [ 1:1 實際像素 ]
             ↑ 預設              ↑ 按下去才進入拖曳檢視
```

| 模式 | 顯示 | 用來回答的問題 |
|---|---|---|
| **符合視窗（預設）** | 整張縮到看得完 ＋ **套疊比例框**（實線＝目標、虛線＝基準）＋ 三態色帶 | 「這個尺寸跟螢幕比是大是小？」 |
| **1:1 實際像素** | 不縮放 ＋ **呼吸燈紅框／置中黑邊／靜態綠框** ＋ 手爪拖曳 | 「1px 的線條實際長什麼樣？相位對不對？」 |

**還有一個小問題需要你確認（D5-a，見 §7）**：Bruce 的原文說的是「大於**目前螢幕**的解析度」，語感上比較像**全畫面預覽**（拿整個螢幕當畫布）；但主頁的預覽是一個小框，這時比較基準就變成「預覽框」而不是「螢幕」。這兩個基準會給出不同的結論（例如 2560×1440 小於螢幕、卻大於主頁的小預覽框）。我的建議是**兩個都做且基準各自標明**，細節見 §7 D5-a。

**檔案**：`docs/baseline/pattern_v1_9_0_golden.txt`（每行 `畫面id|寬x高|反相|FNV1a雜湊`）
**組成**：34 畫面 × 3 尺寸 × 反相 2 態 = **204 組**（Bruce 原文寫 102，那是 34×3；再乘反相才是 204）

**尺寸選擇：3840×2160 / 2560×1440 / 1920×1080 — 固定的裝置像素，刻意不綁當下螢幕。**

> ⚠️ 這一點是踩過坑之後改的。第一次產基線時用「CSS 尺寸 × 當下 dPR」，結果**執行到第 17 筆時 dPR 從 2 掉到 1**（螢幕變成 1920×1080），前 17 筆是 3810×1916、後面變成 1905×958，整份基線混了兩種尺寸而且**當下看不出來**——它甚至偽裝成一個假的「bug」：`center256` 看起來反相有效，實際上只是那兩筆的畫布尺寸不同。

**產生方法**（可重現）：本機 http server 載入 → `#pg-fs` 加 `.on` → 每筆先依 `目標尺寸 / 當下 dPR` 設 overlay 的 CSS 尺寸 → 走完整的 `pgSelectPattern()` 流程 → `pgRenderFill()` → **驗證 `canvas.width/height` 確實等於目標裝置像素**（不符即記錄為 bad）→ 對整張 `Uint32Array` 做 FNV-1a。

**加固措施（必須保留在驗收腳本裡）**：
1. 每筆都驗證 canvas 實際尺寸，不符就記錄失敗——不要相信 dPR 不會變。
2. 產完立刻**整批重跑一次比對**，確認 204 組完全一致，再存檔。
3. **分頁必須在前景**：背景時 `setTimeout` 被節流到 1 秒，實測從 344 ms/組惡化到 48 秒/組（差 140 倍），而且慢到會讓人以為程式掛了。

| R255 | `Gray Level` | 顏色 R、**灰階 255** | 同上 |
| G255 | `Gray Level` | 顏色 G、**灰階 255** | 同上 |
| B255 | `Gray Level` | 顏色 B、**灰階 255** | 同上 |

#### 三個實質差異的處理

| 差異 | 處理 |
|---|---|
| 走選單要 3–5 下 | ✅ 捷徑本身就是為了解決這個，1 下到位 |
| 進入後預設灰階 127 而非 0/255 | ✅ **捷徑必須帶對灰階**。實作上不是「呼叫 `pgSelectPattern` 後再改 level」，而是讓捷徑定義成 `{ menuId, overrides:{colorIdx, level} }`，由**同一支** `pgSelectPattern(id, overrides)` 一次套用 — 避免中間狀態閃一下、也避免兩條路徑分岔 |
| **走選單會進 pattern 模式，4×4 不能再手改** | ⚠️ **見下方 D1-a，這一項不自行拍板** |

#### D1-a — ✅ 已裁決：**丙（兩個都做）**：捷徑要不要切模式？

問題本質：`pgSelectPattern()` 會把 `pgMode` 設成 `'pattern'`（行 1925），此後編輯器變成唯讀反推顯示，手改任一格就 `pgLeavePattern()` 跳回 subpixel（行 834）。而快速樣式原本的價值之一，正是「載入一個起點**再手改**」。

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **甲：捷徑不切模式** | 捷徑仍停在 `subpixel`，但 `pgLevels` 的值**不是寫死的常數，而是即時從對應選單項的實際輸出反推**（重用 `pgSyncGrid` 現成的 `pgDrawSlice` → 取左上角 `pw × ph` 機制，行 1738–1748） | 完全滿足「共用同一份資料來源」；**保留可編輯**；1 下到位 | 只對「4×4 週期內」的畫面成立。目前 5 顆都是 1×1 純色，沒問題；但**未來想把非週期畫面（如 SMPTE）放進捷徑就做不到** |
| **乙：捷徑就是選單，另補一顆「轉為可編輯」** | 捷徑照走 `pgSelectPattern` 進 pattern 模式；在畫面參數區新增一顆 `⇩ 以此為起點手動編輯`，把目前重複單元複製進 4×4 並切回 subpixel | 語意最乾淨（捷徑 100% ≡ 選單）；任何畫面都能當捷徑 | 要手改就多按 1 下 |
| **丙：甲 ＋ 乙都做**（我的建議） | 捷徑走甲（不切模式、值從選單反推）；**同時**在 pattern 模式加乙那顆按鈕 | 兩邊的好處都有；而且乙那顆按鈕**順帶解決一個現存痛點** — 現在從選單選了一張週期畫面後想手改，只能「隨便動一格 → 被踢回 subpixel → 值還在」，這是靠副作用達成的，很不直覺 | 工作量最大（但也只多一顆按鈕 ＋ 一支複製函式） |

**✅ 裁決：丙。** 理由成立且經 Bruce 確認：甲和乙解決的其實是**不同的問題**（甲解決「捷徑要快又要能改」，乙解決「從選單進來之後想改」），現在後者是靠 `pgLeavePattern` 的副作用矇混過去的，本來就該補一個正式入口。

**實作要點**：
- 捷徑（甲）：不切模式，`pgLevels` 的值從對應選單項的**實際輸出即時反推**（重用 `pgDrawSlice` → 取左上角 `pw × ph`，行 1738–1748）。**注意這條路徑同樣受 §0 H1 約束** —— 反推時傳入的邏輯 `W/H` 必須與實際顯示尺寸一致，不可用縮小的代理尺寸，否則含 H 的相位圖會反推出錯的值。
- 「以此為起點手動編輯」（乙）：放在 pattern 模式的畫面參數區，按下後把目前重複單元複製進 4×4 並切回 subpixel。**該畫面非 4×4 週期時此鈕要 disabled**（`pgPeriod === null`），並顯示原因，不要讓使用者按了沒反應。

## 九、本規劃所有實測的方法與紀錄

環境：本機 `python3 -m http.server 8899` 服務 repo 根目錄（避免 GitHub Pages edge 快取與 `file://` 問題），Chrome 開 `http://127.0.0.1:8899/pattern.html`，dPR = 2，overlay CSS 尺寸 1905 × 958 → canvas 3810 × 1916。測完已關閉分頁並停掉 server。

**9-1 逐像素比對法**：`ov.classList.add('on')` → `pgRenderFill()` 畫到 `#pg-fs-canvas` → `getImageData` 取整張 → `Uint32Array` 逐元素 FNV-1a。7,299,960 個像素**全掃，非抽樣**。負向對照（`skipsub` 反相 on/off）雜湊不同，證明有鑑別力。→ §2-1

**9-2 任意尺寸繪圖**：改 `#pg-fs` 的 inline `width/height` → `pgRenderFill()` → 讀 `canvas.width/height` 與 `pgTargetSize()`，並在三個尺寸下取三個相對位置的像素比對。→ §4-1-1

**9-3 resize 不同步**：`pgSelectPattern('skip2_2v2h')` 建立基準 → 改 overlay 高度 → `dispatchEvent(new Event('resize'))` → 比對 canvas 前兩列與 `pgLevels` 前兩列 → 再手動 `pgSyncGrid()` 比對。→ §8 #1

**9-4 資訊框不在 canvas 上**：選 `xy` → `pgRenderFill()` + `pgUpdateInfo()` → 掃 canvas 第 0 列前 40 px 是否有非黑像素（結果 false），同時讀 `#pg-info.textContent`（`1905,958`）與 `tagName`（`DIV`）。→ §4-1-2 #10、§7 D4

**9-5 遮罩 pad 比例**：直接呼叫 `window.pgMaskRects(W, H)`，pad = 40、6 等份露第 2 份，取三個 W 的露出區寬度。→ §8 #4

**9-6 checker 格寬**：n = 256（`ckIdx = 7`），掃第 0 列前 64 px 的連續同色段長度。→ §8 #9

**9-7 黃金基線（第二輪新增）**：見 §6-0。含一次失敗的教訓 —— 第一次產基線時綁「CSS 尺寸 × 當下 dPR」，中途 dPR 從 2 掉到 1 導致基線混合兩種畫布尺寸，並偽裝成一個假的 `center256` 反相 bug。修正為固定裝置像素、每筆驗證 canvas 尺寸、整批重跑比對之後，204 組 0 差異、0 尺寸不符，並與原始碼推導的「不讀 `inv` 的 10 個畫面」完全互相印證。

**9-8 存檔保真度與 BMP 編碼器（第三輪新增）**：見 §4-1-3。四項實測：
1. PNG 往返（512×512，含像素棋盤＋全 256 階灰）：`alpha:false` 與 `alpha:true` 皆 **0 / 262,144 差異**
2. **負向對照**：`rgba()` ＋ `fillRect` 路徑，256 級 alpha 中 **196 個反預乘後 RGB 偏離原值** → 證明預乘風險真實存在，只是我們的 `putImageData` 直寫路徑碰巧避開
3. `colorSpace` 實測為 `srgb`
4. **BMP 24-bit 編碼器原型**（刻意用 513×257，寬非 4 倍數逼出 `pad=1`）：檔案大小與理論值相符、解碼尺寸正確、**逐像素 0 / 131,841 差異** → BGR 排列、padding、bottom-up 三項均正確

**本輪未執行的驗證（做實作時必須補）**：多尺寸批次存檔的正確性、真實滑鼠拖曳的端到端、呼吸燈動畫的實際觀感、手機實機版面。

## 附錄：本規劃不改變的既有設計（明列，避免重整時誤傷）

1. **選單三入口共用同一棵樹**（主頁下拉 2474 / 全畫面面板 2481 / 右鍵 2495）。
2. **全畫面對 overlay 元素本身 `requestFullscreen`**（1061），不是對 `documentElement` — 這是 v1.2.0 解決「工具列吃掉高度」的關鍵。
3. **`html.pg-fs-lock` 鎖捲軸**（159–164）— 沒有它右側會出現捲軸，viewport 寬被吃掉、1:1 直接破功。
4. **1:1 平鋪走 `putImageData` 逐裝置像素直寫**（996–1016、1203–1212），全程無縮放無內插。
5. **遮罩用「存露出區 → 整面蓋 → 貼回」而不是 `clip`**（1823–1839）— `putImageData` 無視 `clip`。
6. **週期偵測從 `pgDrawPattern` 的實際輸出反推**（1624–1700），不維護第二份週期定義表。
7. **`pgSyncGrid` 用 `setTimeout` 而非 `requestAnimationFrame`**（1758–1763）— 背景分頁 rAF 不執行。
8. **鍵盤刻意不統一**（1977–1981）— 每張畫面吃的鍵不同是照原程式的行為，不是疏漏。
