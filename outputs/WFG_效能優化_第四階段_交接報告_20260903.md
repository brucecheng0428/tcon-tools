## 0. 一句話

第四階段做完的是「**LS 預計算不再建出永遠不會被讀的 99.6% 事件物件**」（v4.43.2）；

## 1. 🔴 最重要的更正：`heapUsed` 不含 ArrayBuffer 的 backing store

**前三階段的所有記憶體數字都只量了 `process.memoryUsage().heapUsed`。**
Node 的 `heapUsed` **不包含 `ArrayBuffer` 的 backing store** —— 那些算在 `external` /
`arrayBuffers` 這兩個欄位裡。

後果具體到數字：

| | 前三階段報的 | 第四階段實測 |
|---|---|---|
| frame=1000 全覽的「峰值」 | 349 MB（只有 heapUsed） | heapUsed **267.0 MB** ＋ **arrayBuffers 484.0 MB** ＋ rss 887.8 MB |

也就是說「峰值 349 MB」這個數字**漏掉了佔比更大的那一半**，而且漏掉的正好是
`Float32Array`（`settled` / `lineMinMax` / `minMaxPyramid`）—— WFG 類比通道記憶體的真正大宗。
第三階段之所以會把「事件物件 267 MB」當成最大宗，就是因為事件物件恰好落在 heapUsed 裡、
而 `Float32Array` 落在看不到的地方。

### 🔴 規則（往後量 WFG 記憶體一律照做）

> **一律同時列 `heapUsed`、`arrayBuffers`、`rss`，並各自標明「峰值」與「結束值」。**
> 只報其中一個等於報了一半。峰值要在**每算完一條通道**時取樣（峰值必落在通道邊界附近），
> 不能只在頭尾各量一次。

`_tmp_verify_p4.js` 已經照這個規則寫好，直接沿用即可。

## 2. 本階段實際做了什麼（v4.43.2）

### 根因

v4.41.2 的週期拼接命中之後，`_wfgPrecomputeLsChannel()` 的兩條逐行迴圈都在
`rel = _perDet`（偵測窗 4 個 frame）就收工、剩下整段交給 `copyWithin` ——
**它們一次都不會再讀 `events`**。但 `_wfgLsBuildEvents()` 照樣按整個視窗把事件全部建出來。

實測（FHD 60Hz Single Gate ／ 一進一出 Multi-CPV ／ frame=1000 ／ 全覽，13 條 LS 通道）：

| | 每條 CKO | 13 條合計 |
|---|---|---|
| 建出的事件物件 | 362,001 | 4,346,012 |
| 兩條迴圈實際消費到的 | 1,449 | 17,396 |
| **利用率** | **0.40%** | **0.40%** |

週期在第 1,626～1,630 行命中（各通道略有差異），迴圈停在 `rel = 4,448`。

🔴 **所以正解不是交接文件寫的「分段串流產生 events」** —— 消費者根本不需要「分段餵」，
它需要的是「別建」。串流只會把同樣多的物件分批建出來，省不到重點。

### 改法

`_perP` / `_perDet` / `_perOn` 提前到函式前段算，events 只建 `[base, base + _perDet + 2)`。

- **截斷條件 ＝ 既有的「events 反正會被丟掉」那一條**（`_perOn && !_needRc && !is_gate`，
  就是函式尾端 `events = null` 的同一組條件）。近端與 gate **一律全建、一個字不改**
  ⇒ 三個 `precomp.events` 讀取點完全碰不到。
- 週期偵測失敗（`_perL0` 或 `_perL02` 為 -1）⇒ 帶 `_forceFullEvents` 重跑一次全建。
  此時兩條迴圈都已在 `rel = _perDet` 主動收工，白算的只有 4 個 frame（winLen 的 0.4%）。
  `condensed` 沒有 frame 對齊的週期，走的就是這條路。

**能截斷的依據 ＝ 前綴相等性**（`_tmp_probe_p1_prefix.js` 實測）：
`_wfgLsBuildEvents(base, K)` 與 `_wfgLsBuildEvents(base, computeExtent)` 在 `lineX < K-1`
的區間逐值相同。四個 mode × 全部 LS 通道 × 共 **23,348 筆**事件
（`lineX` / `vTarget` / `_reset` / `_term` 四個欄位逐一比對），**不一致 0 筆**。
結構理由：四個 builder 都以 frame 對齊的 `buildStart` 起算、逐邊緣往後產生，
`endLine` 只決定「產到哪裡停」。

### 成效

| 情境（全覽） | precomp 舊→新 | **peak heapUsed 舊→新** | peak arrayBuffers | peak rss 舊→新 |
|---|---|---|---|---|
| individual f1000 | 1301→**493** ms (−62.1%) | 370.3→**267.0** MB (**−27.9%**) | 484.8→484.0（**±0.2%**） | 1002.4→887.8 (−11.4%) |
| dual_cpv f1000 | 795→**475** ms (−40.3%) | 337.4→**260.7** MB (−22.7%) | 483.5→483.9 | 977.1→861.6 (−11.8%) |
| quad_cpv f1000 | 862→**411** ms (−52.3%) | 348.1→**267.5** MB (−23.2%) | 483.5→483.9 | 983.0→870.1 (−11.5%) |
| condensed f1000 | 751→625 ms (−16.8%) | 237.0→238.8 MB (+0.8%) | 487.0→485.9 | 897.7→843.8 (−6.0%) |
| 四個 mode f10 | 雜訊範圍 | −0.7% ～ −2.7% | ±0.3 MB | ±0.4% |

`condensed` 的 +0.8% 是重跑路徑的成本。
**`arrayBuffers` 完全沒動 —— 這是預期內的，本版動的是 heapUsed 那一側（事件物件）。**

### 驗收

10 組情境（4 mode × frame ∈ {10,1000} × 全覽，另加 f1000 與 f10 各一組放大到 400 行）：
`settled` / `lineMinMax` / `rcSamples` 逐位元 sha256、`wfgExportConfig()`、`wfgGpios`、
`analog_config`、`wfgDumpPolArea()`、`wfgDumpLsCko(3)`、canvas 全部繪圖呼叫
（含引數，16,204～88,232 筆／組）—— **全部相同**。
真實 headless Chrome 載入本機檔：**0 個 console 錯誤**，版本徽章 v4.43.2，波形正常繪出。

## 3. 剩餘瓶頸的定位與算式

`peak arrayBuffers = 484 MB`。構成（frame=1000 全覽，winLen ＝ 1,112,000 行）：

| 每條 LS 通道 | 大小 | 算式 |
|---|---|---|
| `settled` | **4.45 MB** | winLen × 4 B |
| `lineMinMax` | **8.90 MB** | winLen × 2 × 4 B |
| `minMaxPyramid`（第 1 層以上的總和） | **≈8.90 MB** | 等比級數 ≈ 第 0 層大小 |
| **小計** | **22.2 MB** | |

**× 13 條 LS 通道 ≈ 289 MB**，其餘約 195 MB 是 SD1／Subpixel 通道的同類陣列與暫時配置。

🔴 **這些全部是 O(視窗行數)，與 1400 px 的畫布寬度完全無關。**
全覽時每個像素涵蓋約 794 行，但資料仍然逐行完整存在。

補充：`minMaxPyramid` 由 `lineMinMax` **推導**而來，且第 0 層就是 `lineMinMax` 本身
（共用同一個參考、不另外佔記憶體），第 1 層以上才是額外的 8.90 MB。
所以「壓縮 `lineMinMax`」**不會**連帶壓縮金字塔 —— 兩者要分開處理。

## 4. 未採用的方案：週期壓縮（前綴 ＋ 2 個週期 ＋ modulo 映射）

### 方案內容

週期拼接命中時，`settled` / `lineMinMax` 的內容**定義上**就是
`value(rel) = value(base0 + ((rel - base0) mod P))`（這正是 `_wfgLsTilePeriod()` 寫進去的東西）。
所以可以只存 `[0, _perDet)` 這 4,448 個元素（＝迴圈實際算出來的那一段），
讀取時做 modulo 映射，**逐位元必然一致**（不是近似，是同一個定義）。

- 觸發條件可直接沿用 v4.43.2 已有的 `_evTrunc`（`_perOn && !_needRc && !is_gate`），
  偵測失敗時既有的 `_forceFullEvents` 重跑就是天然的 fallback。
- 估計效益：`settled` 58 MB ＋ `lineMinMax` 116 MB ＝ **約 174 MB**，
  484 MB → 約 **310 MB**（−36%）。
- 🔴 **原先估的「484 → 195 MB」是高估的。** 那個估算把 `minMaxPyramid` 的 116 MB
  也算進去了，但金字塔是從 `lineMinMax` 推導、且以**完整視窗長度**materialize，
  壓縮 `lineMinMax` 不會讓它跟著變小。要一起壓縮金字塔必須改動
  `_wfgPyramidRangeMinMax()` 的聚合方式（見下）——那是另一件事、另一種風險。

### 為什麼未採用

> **Bruce 2026-09-03 裁示：「效能其實目前我覺得已經很不錯了，所以以功能不動為最高優先，
> 沒辦法再降就算了。」**

**不是技術上不可行，是風險／收益比在這句裁示之後不成立。**
`precomp.settled` 是 cursor 讀值與量測的資料來源，改它的儲存佈局屬於「動到功能」的範圍。

### 日後若要重啟，這些是前置條件

1. **硬條件是「值」不是「佈局」**：modulo 映射回傳的值必須與現行逐位元相同。
2. **必須涵蓋跨週期邊界**：`rel = _perDet - 1` → `rel = _perDet`（第一次觸發映射）
   與 `rel = base0 + P - 1` → `base0`（繞回）這兩個接縫是最容易錯的，一定要各取點驗。
   另外要驗前綴段（`rel < _perDet`）與最後一個 frame。
3. **必須有 fallback**：週期偵測不成立（`condensed` 現況）走現行完整陣列，且 fallback 也要驗。
4. **消費者清單**（`.settled` / `lineMinMax` 的全部讀取點，已盤點過）：
   - `_wfgClampRel()`（兩處用 `precomp.settled.length` 當視窗長度 —— 壓縮後必須改讀虛擬長度）
   - `_wfgEnsureLineMinMax()`（LS 走提早 return，不受影響；SD 才會用到 `settled.length`）
   - `_wfgBuildMinMaxPyramid()`（`count0` 要改成虛擬長度；第 0 層的讀取要映射）
   - `_wfgPyramidRangeMinMax()`（`lvl === 0` 時 `arr[bi*2]` 要映射；`maxB` 要改用每層的實際筆數）
   - `wfgSamplesFromPrecomputed()`：`initVoltage`、band 的
     `else if (precomp.lineMinMax)` 分支、`settled[]` fallback 分支
   - `_wfgLsVoltFactory()` 走 `events` 不走 `settled`（gate 專用），不受影響
   - 主波形 cursor 的吸附走 `_wfgTransitionCache` 的數位邊緣，不讀 `settled`
5. **失效模式是「大聲」的**：漏改的讀取點在 `rel >= _perDet` 會拿到 `undefined` → `NaN`，
   會直接反映在繪圖呼叫雜湊與 dump 上，不是靜默錯誤。這一點對驗收有利。
6. **金字塔要一起壓縮的話**：每一層在索引空間的週期是 `P / gcd(P, 2^lvl)`
   （P=1112、lvl≥4 時 `gcd = 8`）。但 `_wfgPyramidRangeMinMax()` 是
   **超取樣近似**（把像素範圍向外擴到整數個區塊，且區塊以**絕對行號**對齊），
   `wfg.html` 第 7390 行附近有 🔴 警告：v4.5.5 曾因為分塊對齊改錯，
   SD1 在 lpp≥16 時 band 最大差 **5.0 V**（band 全幅才 9.6 V），
   **逐陣列比對完全抓不到**（差的是聚合方式不是資料）。
   ⇒ 這一塊要動，必須以 `bandData` 逐值比對當閘門，不能只比中間陣列。

## 5. 另外兩個要更正的結論

### 5.1 「② samples 由物件陣列改 typed array」的前提不成立

`wfgSamplesFromPrecomputed()` **只有 `visibleLines <= 500`（Path 1）才建物件 `samples`**。
frame=1000 與 frame=10 的**全覽都走 Path 2**（`bandData` 是 `Float32Array`，零物件）。
實測放大到 400 行可見時，整體 peak heapUsed 只有 **181.1 MB**、arrayBuffers **18.7 MB**，
新舊版完全相同。**不是瓶頸，不要做。**

### 5.2 空白對照：有兩個指紋的鑑別力本來就是 0

第一版比對報「8 組情境全部不一致」，實際上是**指紋自己壞掉**：

| 指紋 | 為什麼不可重現 | 處理 |
|---|---|---|
| `wfgExportConfig()` | 帶 `_exportDate: new Date().toISOString()` | 字串層 `replace` 掉 |
| `wfgDumpPolArea()` | 帶 `ms` / `baseMs` / `calcCount` / `baseCalcCount`（計時與呼叫次數） | `JSON.stringify` 的 replacer 剔除 |

🔴 而且第一次修正**等於沒修**：`wfgExportConfig()` 回傳的是**字串**
（`JSON.stringify(config, null, 2)`），不是物件 —— 套 `JSON.stringify(c, replacer)`
去剔 `_exportDate` 完全無效，又白跑了一輪 16 個 case。

**流程結論**：拿指紋當證據之前，**先跑空白對照**（同一個舊版跑兩次），
確認每一項指紋都全等；有不等的先找出易變欄位剔除、再跑一次空白對照確認，才開始比新舊版。

## 6. 誠實限制

- **Linux headless jsdom 不是 Windows Chrome。絕對秒數與 MB 一律不可對應**，
  只有「同一支腳本、同一環境、優化前後」的比值有意義。
- **時間指標在這個 VM 上雜訊可達 ±80%**（同一格重跑互有高低，例如
  `individual f10` 的 precomp 量到過 53 ms 與 122 ms）。
  **只有記憶體是決定性的**；時間要多次取中位數，或直接標明是雜訊。
- jsdom 的 canvas 是錄音式 stub，比對的是「繪圖呼叫序列與引數」，
  不是實際像素。真實像素的驗證要靠 headless Chrome 截圖（本階段做過冒煙測試）。
