1About this tool

Panel Signal Simulation & Sampling is a pure web-based timing waveform simulator. It turns TCON Phase Counter parameters into visible waveforms without a real panel attached.

What does it do?

Inside a TCON (Timing Controller), a set of register parameters describes when each output signal goes high and when it goes low. These parameters (ACT_TYPE, R_PH, F_PH, ST_LINE, SP_LINE, R_DLY, F_DLY…) are coupled to each other, so the numbers alone make it hard to picture the real waveform.

This tool computes the waveform from those parameters in real time and draws it on screen. Change one number and the waveform updates immediately. Use it to:

  • Practice and teach — see how each Phase Counter parameter actually affects the waveform
  • Verify up front — confirm the timing relationships before you program a real device
  • Rehearse measurements — use the built-in cursors, pulse counter and live readouts to mimic what you do on a scope or logic analyzer
  • Share setups — export a .txt config file or copy it to the clipboard so a colleague can reproduce the same waveform

2Quick start

First time here? Follow these six steps and you will see a waveform.

Open the tool and check the mode

Open Panel Signal Simulation & Sampling, then check that the mode tab in the header is set to "Panel Signal Simulation" (it is the default).

Load an example from the Preset dropdown

In the Preset dropdown at the top left, pick FHD 60Hz Single Gate (LS: Multi CPV). This fills in the system settings, all 18 digital signals, the Level Shifter settings and 18 output channels at once, and a complete waveform appears immediately. Start from a preset the first time rather than building everything from scratch.

Expand System Settings for the timing skeleton, then drag the sliders in System Simulation

Vactive / Vblank / Hactive / Hblank / Frame Rate in the System Settings card define the timing skeleton of the whole frame (VTOTAL, HTOTAL, TCON HTOTAL and Pixel Rate are computed read-only values that you cannot edit). Once they are set, drag the three sliders in the orange-framed System Simulation card below to see what happens when you change the refresh rate or enlarge Vblank — the waveform and every value recalculate instantly.

Try adjusting one signal

Expand Digital Signals → open CK1 → drag the R_DLY slider. CK1 shifts left or right in the waveform view in real time. Every field is computed live; there is no Calculate button.

Measure with cursors

Press 1 to drop cursor A1 (it follows the mouse), then left-click at the position you want to pin it. Press 2 to drop A2. The Time Base Cursors panel on the right shows the time difference between them and the equivalent frequency.

Export the config and share it

Export in the File group of the toolbar downloads a .txt config file. Copy puts the same content on the clipboard, so you can paste it straight into a chat app for a colleague, who reproduces the identical waveform with Paste. On a phone, if the browser blocks automatic clipboard reads when you tap Paste, a Paste Configuration dialog opens so you can long-press and paste it in yourself; it applies the same way.

Works on a phone too The layout is mobile-first. On a phone, drag with one finger to pan the waveform and pinch to zoom. The parameter cards on the left are collapsed by default; tap a card title to expand it.
Do not expect it to match real hardware This tool simulates the ideal waveform derived from the parameters. It does not model real analog RC rise / fall behavior, noise or loading effects. Use it to verify timing relationships, not electrical characteristics.

How the parameters relate to each other

  • 🔴 VTOTAL and HTOTAL are read-only displays, not input fields. What you type are the four ACTIVE ＋ BLANKING fields, and the totals come from adding them up: VTOTAL = Vactive + Vblank, HTOTAL = Hactive + Hblank. To change a total, change one of those four fields.
  • Htotal × Vtotal = the total number of clocks in one frame
  • Pixel Rate = Htotal × Vtotal × Frame Rate, read-only. Only those three parameters decide it, so raising TX DCLK does not change it
  • RX DCLK = Pixel Rate ÷ 2, a read-only display that you cannot type into (you can still move it indirectly with the RX DCLK slider in the System Simulation card, which really works backwards from Frame Rate)
  • TX DCLK accepts manual input, but it is always ≥ RX DCLK. Under Fixed Clock, changing TX DCLK does not feed back into Frame Rate; under Variable Clock it does (two-way linkage, see the dedicated section below).
  • TCON UI DCLK = TX DCLK × the model factor. It accepts manual input and is linked both ways with TX DCLK (edit either field and the other is recomputed at once)
  • TCON HTOTAL and the HTOTAL above it are not the same number. It is called out separately so that you check it - see "How the two HTOTALs differ" below
  • TCON Pixel Rate = VTOTAL × TCON HTOTAL × Frame Rate, read-only. It differs from the Pixel Rate on the left only in which Htotal it uses, so raising TX DCLK makes it grow (the one on the left does not) - see "How the two Pixel Rates differ" below
  • Vactive / Hactive only affect where the active display area is marked; they do not change the total time span. And they have no lower-limit protection whatsoever - whatever you type is what you get
🔴 How the two HTOTALs differ - why TCON HTOTAL is highlighted in light blue The same H Total box holds two numbers, and it is easy to read them as a duplicate:

- HTOTAL (left, white) = the Htotal on the system side, that is Hactive + Hblank, the value you just typed in yourself. It describes how long one line is on the panel / system side.
- TCON HTOTAL (right, light blue) = the Htotal the TCON actually uses internally. It is converted from the value on the left by the TX/RX DCLK ratio: TCON HTOTAL = round(HTOTAL × TX DCLK ÷ RX DCLK). So the two match exactly only when TX = RX; raise TX DCLK and the right-hand number separates from the left.

🔴 Gate Type is not a term in this formula. Measured: switching Single ⇄ Dual leaves TCON HTOTAL identical value for value (2200 → 2200; a second case, 2560×1440@120 Dual with TX 300, also matches the formula). Gate Type affects Line Buffer and the internal timing calculations, not TCON HTOTAL.

It is not another parameter for you to fill in. It is a reference readout: compare it with the HTOTAL in your TCON config file or in the official UI, and only when they agree does this simulation describe the same thing as the real hardware. That is exactly why it is highlighted - it tells you to look at this field, not to edit it.
🔴 How the two Pixel Rates differ (the bottom of the card has two columns) The structure is exactly the same as the two HTOTALs above - white on the left = system side, light blue on the right = TCON internal - and they sit directly below HTOTAL / TCON HTOTAL, aligned so the correspondence is easy to see:

Pixel Rate (left, white)
HTOTAL × VTOTAL × Frame Rate
- Uses the system-side HTOTAL
- Raising TX DCLK does not change it

TCON Pixel Rate (right, light blue)
VTOTAL × TCON HTOTAL × Frame Rate
- Uses the TCON internal TCON HTOTAL
- Raising TX DCLK does make it grow

The two results are supposed to differ, and that is not an error - it is exactly why this version puts them side by side. For example:
2560×1440@120, Hblank 160, Vblank 40, TX DCLK 300 ⇒ HTOTAL 2720 / TCON HTOTAL 3378 ⇒ Pixel Rate 483.072 / TCON Pixel Rate 599.9328.

Which one to read when: to judge whether the timing is reasonable for the panel / signal source, read the left one; to reconcile against the internal clock in a TCON config file or the official UI, read the right one.
Check the model before you copy a DCLK from the TCON UI Different TCON families mean different things by the DCLK shown in their interface:
- The EM01 family and every NB TCON (E501A / E501B / E503 / EN01) → factor ×1, so the number in the UI equals TX DCLK
- EM02 / E512 (same family; E512 came first and EM02 is its revision) → factor ×2, so the number in the UI is twice TX DCLK
In the default state (TX DCLK = RX DCLK) an EM02 UI therefore shows the whole Pixel Rate (148.5, for example) while EM01 shows half of it (74.25). Typing the 148.5 you read on an EM02 UI straight into TX DCLK is off by a factor of two - put it in the TCON UI DCLK field instead, and make sure the model on its left is the right one.

Note that "UI = Pixel Rate" and "UI = Pixel Rate ÷ 2" are only what comes out in the default state, not identities. The factor multiplies TX DCLK: once you raise TX DCLK, UI DCLK follows TX while Pixel Rate stays put.
TX DCLK and TCON UI DCLK have hard lower and upper limits Arrow keys, the mouse wheel and the spinner arrows stop at the limit and go no further down (or up). Typing a value outside the range is rejected before it is applied, with the reason shown in place, and the original value is kept. The tool neither silently clamps to the limit nor applies the value and snaps back.

The range comes from two constraints stacked together:
- TX DCLK ≥ RX DCLK (a constraint that has always been there)
- The model spec for TCON UI DCLK: Monitor (EM01 / EM02 / E512) 40 – 500 MHz; Notebook (E501A / E501B / E503 / EN01) 20 – 105 MHz
Both fields derive their limits from the same calculation, so one field never blocks a value that the other lets through.

🔴 The screen tells you the way out when you exceed what the model can do, spelled out in one sentence, for example:
"At this resolution E503 tops out at 90 Hz, and you are at 144 Hz. Lower Frame Rate first, then VBLANK / HBLANK become adjustable."
You normally see this because you imported a code / config file that exceeds what this model can do (typing cannot get you into this state, because the input fields block it first). Do what it says: bring Frame Rate below the number it names and the other fields unlock again.
Fixed / Variable Clock follows the model Notebook TCONs (E501A / E501B / E503 / EN01) are always Fixed Clock, so when you pick an NB model, Variable Clock greys out and the tool switches back to Fixed Clock automatically.
Monitor TCONs (EM01 / EM02 / E512) can be either, and the tool leaves your current choice alone.
Your own choice is remembered: pick Variable Clock on an MNT model, switch to NB (forced to Fixed Clock), then switch back to MNT and it returns to Variable Clock. Changing the model does not eat your choice.
A larger Frame Repeat Count costs more resources It decides how many frames to simulate (1–4096). The default of 10 is enough for most timing work; raise it only when you need to watch Toggle behavior that spans many frames (an FRM_NO cycle, for example). At a few thousand frames the first draw takes a while.

🔴 The V-Blanking slider: while you drag it, not one digit of Pixel Rate or RX DCLK changes That is the only reason this slider exists, and it is the biggest difference between it and editing the Vblank input field directly:

- Edit the Vblank input field ⇒ VTOTAL grows, Frame Rate stays put ⇒ Pixel Rate grows with it.
- Drag the Vblank slider ⇒ VTOTAL grows and the tool lowers Frame Rate proportionally to compensate ⇒ the product Pixel Rate = HTOTAL × VTOTAL × fps is unchanged, and RX DCLK naturally does not move either.

What it is for: "This TCON has only so much bandwidth. If I want more vertical blanking, how much Frame Rate does it cost?" One drag answers that, with no arithmetic on your side.

The two end points:
- Left end = the Vblank value you last typed by hand, as of the moment the slider appeared. After dragging up you can always come back, because the left end is never pushed up by your own dragging (otherwise one drag up would strand you). To set a new left end, type a new value into the Vblank input field.
- Right end = 65535 (the register bit-width limit).

A fractional Frame Rate will show up, and that is normal. Holding Pixel Rate constant makes an exactly whole-number Frame Rate almost impossible (only 19 of the 65535 Vblank values land on a whole number). This path therefore uses full-precision floating point on purpose. Fractions come only from this path: the Frame Rate input field still accepts whole numbers only, and the Frame Rate slider still steps one unit at a time.
The view stays put while you drag a slider Dragging the Frame Rate slider and dragging the Vblank slider both anchor on the center of the waveform area: if you were watching a spot in frame 5, you are still on that same spot in frame 5 when the drag ends, with nothing to hunt for.
The Vblank slider is where you notice it most, because it changes VTOTAL. The anchoring applies to every path that changes VTOTAL (sliders, the Vblank / Vactive input fields, importing a config file), not only to sliders.

4-4 Which fields have lower-limit protection and which have none

🔴 H-Active and V-Active have no limits at all - whatever you type is what you get These two fields are the resolution of the panel. That is a fact, not a number the tool gets to correct. So:
- No lower-limit protection, never rewritten to some other value by the tool, and not included in the internal boundary audit.
- Type 800 and you get 800. Even if the resulting TCON UI DCLK falls below the model spec minimum, the tool still does not block you - it only shows a note below, telling you that the current state is out of spec and how to get back into the legal range.
(The one exception is the total upper-limit check: push the resolution past what the model can do and the tool rolls ACTIVE back. That is a different matter from the lower limits discussed here.)

By contrast, V-Blanking and H-Blanking do have lower-limit protection, built from two layers with the larger of the two winning:

LayerValueWhere it comes fromWhen it applies
① Hard floor 10 A minimum stated outright, with no derivation. Blanking that small has no meaning on real hardware anyway. Always
② Derived from the model spec The smallest blanking derived backwards from the current model's TCON UI DCLK spec minimum Blanking too small ⇒ HTOTAL / VTOTAL too small ⇒ Pixel Rate too low ⇒ TCON UI DCLK drops below the spec minimum. Solve that chain backwards and you get the lower limit for blanking. Only under Variable Clock. Under Fixed Clock, TX DCLK does not follow RX downwards, so the constraint never reaches upstream and only the hard floor of 10 is left.

The effective lower limit = max(10, the model-derived value). Type anything smaller and the tool rejects it before it is applied and explains why in place, and not a single bit of the value on screen moves. The two layers have different reasons, so their messages are written separately - hitting the hard floor never drags in an irrelevant reason such as "UI DCLK would fall below spec".

The lower limit only blocks moves that make things worse, so there is always a way back A value is blocked only when it is below the limit and smaller than what was there before. So if you load an old config file whose blanking is already below the limit, moving it up is always allowed and you never get stuck in a state that is both out of spec and frozen.
For the same reason the Vblank slider obeys only the hard floor of 10, not the model layer - dragging it conserves Pixel Rate, so UI DCLK never dips below the spec minimum at any step, and applying the model layer would only shrink the draggable range for nothing.

4-5 TCON UI DCLK ↔ Frame Rate two-way linkage

Precondition: everything in this section applies only under Variable Clock. You pick Fixed or Variable Clock at the top of the TCON Clock Settings card (NB models have Fixed Clock only, and Variable Clock is grayed out).

Fixed ClockVariable Clock
Relationship between TX DCLK and RX DCLK TX may exceed RX, and the two move independently TX ≡ RX, always equal
🔴 May TX DCLK be lower than RX DCLK Never, in either mode. A lower value is rejected before it is applied and explained in place, and the original value is kept (no silent clamping to the limit, and no applying it and snapping back).
Does Frame Rate move after you change TX / UI DCLK No. TX is an independent quantity. 🔴 Yes. Setting the DCLK is the same as setting Frame Rate backwards.
Do TX / UI DCLK move after you change Frame Rate Yes (Frame Rate ⇒ Pixel Rate ⇒ RX DCLK; under Fixed Clock, TX is lifted only when RX catches up with it)
🔴 Under Variable Clock: raise TX and RX rises with it; lower TX and RX falls with it Under Variable Clock TX ≡ RX, so editing either TX or TCON UI DCLK moves the other field and RX DCLK along with it, and then solves Frame Rate backwards from the result:

Frame Rate = 2 × TX DCLK × 10⁶ ÷ (HTOTAL × VTOTAL)

The back-solve conserves the resolution (HTOTAL / VTOTAL); what changes is Pixel Rate.
Example: at 4320×2220, type TCON UI DCLK = 432 ⇒ Frame Rate solves to 90.0901 Hz.

🔴 This path conserves exactly the opposite of what the Vblank slider conserves, so do not mix the two up:
- Vblank slider ⇒ moves VTOTAL, conserves Pixel Rate.
- DCLK back-solve ⇒ moves Pixel Rate, conserves HTOTAL / VTOTAL.

All four controls are live under Variable Clock: the TX and TCON UI DCLK fields and both sliders can be moved, and their left-hand limit is the model spec minimum rather than RX itself, so the whole range is draggable in both directions.

5Other TCON settings (Gate Type / Toggle FRM_NO)

Three frame-number parameters shared by everything. Every digital signal that turns Toggle mode on uses this one set of values; you do not need to set them signal by signal, and you cannot.

What it controls

Toggle mode makes the ACTIVE polarity of a signal flip once every few frames, which is typical of control signals used for polarity inversion. FRM_NO_0/1/2 set the rhythm of the flip, and each signal uses its own TG_INI_VAL to pick which of the three it follows.

The INI_VAL of a Toggle signal is the starting level "at the beginning of each frame" It is not reset once per line. The start of every frame decides the starting level for that frame. This is the point people get wrong most often.
🔴 The first frame never flips The closed form of the polarity is ACTIVE(frame) = base XOR ( floor(frame / (FRM_NO + 1)) & 1 ), where base is the starting polarity given by INI_VAL (0 - Low → 0, 1 - High → 1, Keep → 0 because there is no previous frame to carry over).
Substitute it in and frame 0 always equals base — if the starting polarity is 0 it stays 0, if it is 1 it stays 1. It does not "always start from HIGH".
🔴 1-based / 0-based conversion: "FRM_NO = 99 means the polarity changes every 100 frames, so frames 1 to 100 share the same polarity and frame 101 is the first inverted one" is the 1-based way of saying it. The frame index inside the tool and the code is 0-based, which maps to "frame 0-99 identical, frame 100 inverted".
FRM_NOPeriodACTIVE from frame 0 (b = base)

To see the Toggle effect, Frame Repeat Count must be large enough (at least larger than the FRM_NO value), otherwise the flip never comes around inside the simulated range.

6-0 TCON type (MNT / NB) — a global setting

The TCON type decides how many bits ACT_TYPE / R_PH / F_PH get — their bit width. All digital signals share this one setting; it is not set signal by signal.

・E501A / E501B / E503 / EN01 → Notebook (NB, 6 bit)

XSTB (ACT_TYPE=0, R_PH=0, F_PH=0): ACT_TYPE is 0, so both counters already sit at the maximum from the start and every line is a trigger line for R and for F at the same time. R_DLY and F_DLY are both measured from the start of the same line, so the level rises and then falls inside one line, giving one narrow pulse per line.
VST1 (ACT_TYPE=15, R_PH=15, F_PH=13, ST_LINE=2): R_PH_CNT loads 15 = ACT_TYPE right on line 2, so R_DLY is measured from line 2. F_PH_CNT starts at 13: line 2 is 13, line 3 is 14, and only line 4 reaches 15, so F_DLY is measured from line 4. The two are 2 lines apart, so the pulse is 2 lines wide.

6-2 Toggle mode: a different algorithm (it applies to any signal you check it on)

This is the only part of the 18 signals that needs its own section. Check Toggle and this signal switches to a different algorithm — the criterion is whether Toggle is checked, not what the signal is called. Check Toggle on XSTB, VST1 / 2, CK1–CK8, TEND, VS, HS or GPO0 / 1 and the behavior is exactly the same as XPOL (the same set of parameters produces an identical waveform on any signal). In practice it is used most often on XPOL and LC, but that is convention, not a restriction.

Checking it also adds seven quick-setup buttons to the card. One click fills ACT_TYPE, R_PH and F_PH at the same time with the values of the matching polarity inversion mode, and sets the ST_LINE / SP_LINE line range as well, so you do not have to work them out one by one.

Why are these seven sets called "polarity inversion modes"? The seven sets of values are the standard combinations designed for polarity inversion, and polarity inversion is exactly what the XPOL signal is responsible for — the Source Driver looks at XPOL to decide whether to charge positive or negative Gamma. 🔴 A signal with Toggle checked follows a completely different algorithm from an ordinary pulse signal (this holds for any signal, not just XPOL / LC) An ordinary signal has two counters that each count up to ACT_TYPE, one handling the rising edge and one the falling edge. A Toggle signal has only one counter, and F_PH is not a phase start value but a bitmask:
  1. R_PH_CNT on the ST_LINE line loads R_PH directly (with no modulo: it loads even when R_PH is larger than ACT_TYPE).
  2. It then updates once per line, and two things can reset it to zero:
    ① the value on this line equals ACT_TYPE → the next line is zero (the normal period, length = ACT_TYPE + 1)
    ② adding one overflows → it wraps at the bit width of the TCON type (MNT 9 bit at 511, NB 6 bit at 63, see 6-0)
    Written as one line: cnt(n+1) = (cnt(n) == ACT_TYPE) ? 0 : ((cnt(n) + 1) & maskBits).
    Together they produce one behavior that is easy to miss: if the value after wrapping happens to equal ACT_TYPE (with ACT_TYPE = 0, for example), the counter stays locked at 0 from then on and the waveform never changes state again.
  3. Read F_PH in binary and use it as a bitmask: bit(n) = (cnt(n) & F_PH) != 0. For example F_PH = 2 (0b10) → look at bit 1.
  4. The ST_LINE line is driven to ACTIVE unconditionally (with R_DLY applied). The level of every line after it is judged relative to the ST_LINE line:
    bit(n) == bit(ST_LINE) → ACTIVE; different → inverted.
    🔴 Note it is "in phase with the start line or inverted from it", not "bit = 1 means HIGH". Change R_PH and the phase of the whole waveform shifts with it.
    🔴 Note as well that ACTIVE is not the same as HIGH — ACTIVE is the working polarity of this frame, and it can be HIGH or LOW depending on INI_VAL and FRM_NO (see the next item). So the ST_LINE line is not guaranteed to carry a rising edge; it only means "entering ACTIVE".
  5. R_DLY only acts on the line where the level changes, and both directions use R_DLY (low→high as well as high→low). A line with no change gets no delay at all and simply keeps the level of the line before it.
  6. Toggle mode has no F_DLY, and the field does nothing in this mode (the XPOL register table in the official timing document also marks it as unused in Toggle mode, with the actual value set to 0).
  7. SP_LINE is the last line that takes part in the toggle, inclusive. Past it the counter stops counting and there are no more transitions: the level of the SP_LINE line is kept until the frame ends, and the next frame starts over at ST_LINE by reloading R_PH.
  8. Whether ACTIVE is HIGH or LOW for the whole frame: ACTIVE(frame) = base XOR ( floor(frame / (FRM_NO + 1)) & 1 ), where base comes from INI_VAL. frame 0 always equals base, so the first frame never flips; after that it inverts once every FRM_NO + 1 frames. XPOL uses FRM_NO_0 = 0, which inverts once per frame. See chapter 5.

Why does "3-line" look like "positive positive negative" or "positive negative negative" on screen? The name 3-line counts the lines per period, the same naming as every other button in this row. Within one period the polarity of the three lines is positive, negative, positive. But a period starts and ends positive, so the trailing positive of one period runs straight into the leading positive of the next, and a continuous view is really + - + | + - + | + - + — only 1 line in every 3 has the opposite polarity, and the eye reads it as "positive positive negative" repeating.
On top of that, the FRM_NO setting makes XPOL invert everything frame by frame, so the same stretch in the next frame becomes - + - | - + -, which reads as "negative negative positive". With one and the same setting, a different frame or a different starting line therefore reads as "positive positive negative" or "positive negative negative" — both are the same 3-line period with a 2:1 polarity ratio.

When the current ACT_TYPE / R_PH / F_PH all three match the combination behind one of the buttons, that button is highlighted in orange automatically, so you can see which mode you are in at a glance. Change any parameter by hand and the highlight disappears.

6-3 How the parameters stack into the final waveform

Order of operations: ACT_TYPE sets the period → R_PH / F_PH place the edges inside the phase → R_DLY / F_DLY shift them at clock level → ST_LINE / SP_LINE cut away everything outside the range → OAX combines the signal with another one → INV inverts at the very end → if Toggle is on, the initial level flips frame by frame according to FRM_NO.

Two numbers decide everything

  • Sample rate decides how much detail you see. To reconstruct a signal, the sample rate has to be several times its frequency. Measuring a 1 MHz SCL at 200 MHz gives you 200 points per bit, which is what makes the edge positions accurate.
  • Depth decides how long you record. capture time = depth / sample rate, and the toolbar prints that number right under the Sample group (Theoretical capture time).
  • The two pull against each other: recording longer means lowering the sample rate or raising the depth. First ask how long the event you want to catch lasts, then work backwards.
The word "theoretical" is there for a reason When the depth is 1 GSa or more and the theoretical time is over 5 seconds, the tool appends "actual length depends on hardware compression" after the number. The hardware stores data with edge compression, so the busier the signal the shorter the recordable time, and what you actually get is shorter than the theoretical value.

It resumes on its own after the import

When the import finishes, the capture that was interrupted carries on automatically. The contents are stored in this browser on this computer, so from then on pressing capture just works and you never import it again.

Why it cannot download the file for you Browser security does not let a page remember or read the path of your downloads folder, so you have to pick the file by hand once. After that the page keeps it itself and there is nothing to repeat.

Settings that are remembered

  • Kept in the browser: channel names, channel display order, sample rate, depth, threshold voltage, trigger channel / edge / position, and the quick setup currently selected. They are reused after a reload and the next time you open the page.
  • Kept separately: the contents of the device support pack ( stored long term after the first import ).
  • Not remembered: the captured waveform data. To keep it, use Export → full data (.kvdat).
  • To wipe the device support pack and go back to the first-use state, use Clear Firmware State at the bottom of the Settings panel in the toolbar.

20FAQ

Click a question to open the answer.

I changed a parameter and the waveform did not move at all. Why?▼

Work through these, most likely first:

  1. The ENABLE box of that signal is not ticked - the card title shows a gray OFF.
  2. The signal is not assigned to any output channel - check the Output Channels card.
  3. The display toggle of the matching channel is on ○ ( hidden ) instead of 👁.
  4. ST_LINE is larger than Vtotal, or SP_LINE is smaller than ST_LINE, so the signal produces no output at all inside the simulated range.
  5. The current view happens to miss the stretch where the signal is active - press Fit All to see the whole picture.
How fast is wheel zooming after I import a large config file?▼

The amount of computation per redraw is tied to how many pixels are on screen, not to how many lines are in view, so the far end and the near end are both steady at about 33 ms per step ( about 30 FPS ), and the Fit All redraw takes about 0.03 seconds.

🔴 One kind of stall does remain: the freeze right after you zoom all the way out and release the mouse. That one is the pre-computation of the analog signals, a separate topic. See chapter 11.

Clicking the VTOTAL / HTOTAL fields does nothing. Why can I not edit them?▼

Those two are read-only displays, not input fields. What you edit are the four fields above them: VTOTAL = Vactive + Vblank, HTOTAL = Hactive + Hblank. Change any one of them and the total below is recomputed at once.

Why does Frame Rate turn into a decimal when I drag the Vblank slider?▼

That is normal, and it is deliberate. The one purpose of the Vblank slider is to enlarge Vblank while Pixel Rate and RX DCLK stay exactly as they are. Because Pixel Rate = HTOTAL × VTOTAL × fps, the moment VTOTAL grows, fps has to come down in proportion to make up for it - and that proportional value is almost never a whole number ( of the 65535 possible Vblank values, only 19 land on an integer ). Rounding would break Pixel Rate, so this path works in full-precision floating point.

Decimals come from this path and nowhere else: the Frame Rate input field still takes integers only.

Under Variable Clock I changed TX DCLK and Frame Rate moved with it. Why?▼

Under Variable Clock the two are linked in both directions: setting the DCLK is the same as setting Frame Rate from the other end. In a Variable Clock application TX ≡ RX, so moving TX or TCON UI DCLK takes RX with it, and Frame Rate is then derived from fps = 2 × TX × 10⁶ ÷ (HTOTAL × VTOTAL). TX up ⇒ RX up; TX down ⇒ RX down. What that derivation holds fixed is the resolution; what moves is Pixel Rate.

Under Fixed Clock it does not happen - a Fixed Clock TX is an independent quantity, it may be larger than RX, and changing it does not affect Frame Rate. In both forms, though, TX may never be smaller than RX: enter a lower value and it is rejected before it is applied, and the original value is kept.

Under Variable Clock all four controls are live - both TX fields and both sliders - and their lower end is the model spec minimum, so the whole range is reachable in either direction. See 4-5.

I loaded the exported script into the official TCON UI, but the timing on screen is still the old one?▼

There is nothing wrong with the script; the official UI just does not re-read by itself after an import. Go to the GPO tab, press Read once, and the settings appear in the Current sub-tab. Exporting for an MNT model pops up a reminder about exactly this ( NB does not ).

To copy the CURRENT values on into the Normal / 200% / 133% sub-tabs, the correct steps are: ① press Read on the GPO tab → ② switch to the target sub-tab first → ③ click the bottom-left File IO → ④ under --- Copy Data --- choose From Current. Full description in 12-4.

At a panel Gate count of 4 or 8, what happens when a CK pulse runs past the end of the frame?▼

The level state is reset at the frame boundary, so every frame starts from a clean state. Even when the SP_LINE of CK runs past a whole frame and CKO finishes the frame sitting high ( VGH ), the Gate pulse numbering in the next frame still lines up - nothing is shifted by one across the board.

Setups where CKO returns to VGL at the frame boundary anyway ( the vast majority ) are unaffected by the reset.

Does a non-default resolution come back correctly after a reload?▼

Yes. Whatever Hactive is set to ( QHD 2560×1440, for example, rather than the default 1920 ), Hblank, HTOTAL and Pixel Rate all come back with the values you left them at.

The same restore order applies to all three paths: automatic restore, manual config import and paste settings.

Why are some sliders orange and some numbers bright blue?▼

The colors mean something, they are not decoration:

  • Orange = the System Simulation card - once System Settings are done, this is the card you are meant to work on. The card outline, the enlarged title and the thumbs of the three sliders are all orange.
  • Bright blue = ordinary controls ( the two sliders in TCON Clock Settings ), plus the read-only annotated values the TCON actually runs on ( TCON HTOTAL, TCON Pixel Rate ). It is the same blue as the results on the Rx/Tx Frequency Calculator tab.
    🔴 Inside the System Settings card, bright blue means one thing only: a number internal to the TCON. The system-side numbers on the left of the same row ( HTOTAL, Pixel Rate ) are always white.

Full description in 4-2.

Why is there no Calculate button?▼

Every field in Panel Signal Simulation mode is computed live: the waveform is regenerated the moment you type, so there is no confirm button and none is needed. You can drag a slider and watch the waveform change at the same time, which is much more direct than pressing calculate after every edit.

Toggle is ticked but I cannot see anything flipping?▼

Two common causes:

  • Frame Repeat Count is too small. Toggle flips frame by frame, so with FRM_NO set to 99 and only 10 frames simulated, the flip never comes round inside the range. Raise Frame Repeat Count above FRM_NO.
  • The view is too narrow. To see behavior across frames, press Fit All first to reach a scale where several frames are visible.
I pressed a number key and the cursor disappeared. Why?▼

A cursor cycles through three states: off, following the mouse, pinned. Press the same key again while it is following the mouse and it is removed. If you moved the cursor into place but never clicked the left button to pin it, it is still in follow mode, so the next press of that key makes it vanish. The right way is: press the number key, move the mouse where you want it, then click the left button to pin it.

Nothing happens after I type a number into the time-difference field?▼

Three conditions have to be met before it takes effect:

  • Both cursors of that group must already be placed ( with only one of them down, the input field does not appear )
  • The value must be a positive real number, not 0 and not negative
  • Converted to seconds it must be no smaller than 0.5 ns; anything smaller is rejected

Press Enter to apply what you typed ( Esc discards it ).

I drag one cursor and the other one follows it. Why?▼

The time-difference lock is in effect, which means you set the spacing of that group earlier with the time-difference field. The two cursors now move together at a fixed spacing, like a caliper set to a fixed width. To release it, press the × on that group to close it and place the cursors again, or toggle that group of cursors with its shortcut key.

The pulse count on an analog channel is not what I expected?▼

On an analog channel it is the V1 voltage cursor of that channel that decides high from low. Set V1 too high or too low and the count will not match what you expect. Open the V1/V2 cursors next to the channel name first, drag V1 to somewhere near the middle of the waveform swing, and then read the count again.

I changed GOA Phase. Where did the CKO channels go?▼

Changing GOA Phase rebuilds every CKO. Each new CKO goes into the first free output channel and is named "CKO n". If all 64 channels are already taken there is nowhere left to put a new CKO - set the source of the channels you do not need to None first, then set GOA Phase again.

I pressed an XPOL quick-setup button and other fields changed too?▼

That is the intended behavior. Besides filling in ACT_TYPE / R_PH / F_PH, a quick-setup button also sets INI_VAL to 2 - Keep, and when ACT_TYPE is greater than 0 it sets SP_LINE to its maximum of 16383. If you need something different, press the button first and then edit those two fields by hand.

Why is the exported file a .txt and not a .json?▼

The content really is JSON; the .txt extension is purely a convenience. Plenty of messaging tools and mail systems block a .json attachment, while a .txt usually goes straight through. On import, both .txt and .json are accepted.

The waveform will not pan and everything feels sluggish?▼

The usual cause is a Frame Repeat Count set far too high ( in the thousands, say ) while you are also on Fit All, which leaves an enormous amount of data to draw. The fix: zoom into the stretch you actually care about, or bring Frame Repeat Count down to the smallest value you need. The "FHD 60Hz Single Gate" preset loads with Frame Repeat Count at 1000, so if you do not need to look across frames, turn it down first.

Can I rename a channel directly on the left of the waveform?▼

No. The name column to the left of the waveform has no double-click rename and no context menu. Go to the Output Channels card on the left and edit the name field on the matching row. The name beside the waveform updates immediately.

Can I use the simulation result directly as a specification for real hardware?▼

Not advisable. This tool draws an ideal waveform derived from the parameters, for verifying timing relationships. It does not include the RC delay, loading effects, process variation or noise of a real circuit. It will help you find mistakes in the timing settings before you go to the bench, but electrical characteristics still have to come from measurements on real hardware and from the formal specification documents.

What about the LA Analyzer tab?▼

LA Analyzer is a complete, self-contained logic analyzer, and it is covered in chapters 13-18 of this manual: introduction and quick start, acquisition and trigger settings, toolbar, waveform area and channel column, side panels and protocol decoding, hardware link and device support pack.

LA: there is a waveform the moment I open it, and I have not connected anything?▼

That is the demo waveform - with no captured data and no imported file, the tool builds a fake signal from the sample rate and depth you picked, purely so the layout is not blank. It means nothing as a measurement. How to tell: if Decode Results on the right is still waiting for analyzer decode data and there is no imported file name in the header, what you see is the demo waveform.

LA: one channel is flat all the way across. No signal, or a wrong setting?▼

Look at the LED at the far right of that channel name first: no green, and a 0 or a 1 on display means that line had no edge at all during the whole capture. Work through these, most likely first:

  1. The threshold voltage is wrong - measuring a 1.8 V signal on the 2.5 V setting ( Vth 1.25 V ) is still workable, but leave it on the 5 V setting ( Vth 2.5 V ) and it reads 0 forever. This is by far the most common cause.
  2. The probe is not on the pin, or the ground lead is not connected.
  3. The channel is not enabled ( tick it with CH0-15 or in the settings panel ).
  4. The signal really is doing nothing ( the unit under test has not reached that state yet, for example ).
LA: pressing Single does nothing, or it asks me to import a zip?▼

A real capture needs three things: desktop Chrome or Edge, the page opened over https, and a device that is not held by the official software. The first time you also have to import the device support pack once ( see chapter 19 ); after the import, the capture you just started carries on by itself. If you are told the device is in use by another program, close the official software first and then press the hardware link ⏻.

LA: the decode results are a wall of red. Is the panel really faulty?▼

Rule out the decoder settings before you draw any conclusion:

  1. The channel assignment is wrong - SDA / SCL or the AUX channel is pointing at the wrong line. The channel name column shows the analyzer role, so one look settles it.
  2. The DP AUX Bit Rate has been changed - it should be 1,000,000.
  3. The polarity is reversed - try setting Polarity to Invert.
  4. Tolerance is too tight - with jittery signal edges, put it back to 25% first.
  5. Only when all of the above are right is it a genuine fault. Click the badge in the Type column to see the specific reason that entry was judged abnormal.
