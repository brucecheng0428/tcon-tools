1About this tool

When several Source Drivers are chained on one Port, each one sits at a different distance from the TCON, so its data arrives at a different time. This tool works out two things: how to trigger the scope so you can see each driver, and what cof_cnt boundary values to set on the TCON.

What it solves

  • Oscilloscope A Event B setup - to see the waveform of the 3rd driver, how many CLKs must the B event count? Counting by hand is easy to get off by one, so the tool lists every driver at once.
  • UI cof_cnt boundary - in time-division (multi-chip) drive, the TCON has to know at which pixel position it hands over to the next driver. Get the boundary wrong and vertical bands of colour difference appear on the screen.
  • Skew step reference - the step tables for coarse (cksk) and fine adjustment, ready to look up while tuning skew.

Before you start

  • This tool has a "Calculate" button - unlike every other page in the toolbox. It needs the driver count first so it can create the X1…Xn input fields; only once those exist is there anything to calculate.
  • Changing any input collapses the results, a reminder to press Calculate again so you never mistake stale numbers for fresh ones.
  • "X1 is closest to the TCON" - reverse the numbering direction and the whole set of event values is wrong.

2Quick start

Fill in the basic parameters

Use the Hres. dropdown to fill in Hactive, then check that Driver bits, Driver pairs and Single / Dual Gate all match the actual board.

Choose the driver count

Click a number button (1–8) under "Drivers per Port". The X1…Xn input fields only appear once you click, which is why this page needs a calculate button.

Fill in the oscilloscope event count

Measure the number of CLK events between the XSTB(TP) rising edge and the mLVDS RST falling edge, then enter it. Click the diagram to enlarge it and see the trigger definition.

Fill in the channel count of each driver

Once X1 is filled in, the remaining Xn follow it automatically (unless you edited one by hand). Enter them one by one when they differ, or press Copy to All to overwrite them all.

Press "▶ Calculate"

You get two tables: on the left the B event value of each driver (for the scope), on the right the cof_cnt boundary values (for the TCON). Switch the TCON model between EM01 and EM02 in the top right corner.

Disappearing results are not a fault Touch any input field and the result area collapses - those numbers no longer match the current input. Finish editing, then press Calculate again.

What you measure

The full name of the field is "CLK EVENTs from XSTB(TP) rising to mLVDS RST falling", which means:

A: XSTB(TP) rising edge
→
Count mLVDS CLK edges
→
B: RST falling edge
  • Set the scope trigger to A event B mode
  • A = XSTB(TP) rising edge
  • B = mLVDS CLK, both edges (both edges count, because mLVDS is DDR)

Enter the number you measured. The B event value of every driver after that counts up from this number.

Formulas

TargetB event valueDescription
X1 (first driver)floor( floor(X1 × bits ÷ pairs ÷ gate) ÷ 2 ) + EventsFirst work out how many CLKs the data of one driver occupies, then take half of it (that lands in the middle of that driver's data, which is easier to trigger on), and add the starting event count you measured.
X2 … Xnfloor(Xn × bits ÷ pairs ÷ gate) + previous valueA running sum. Each further driver waits one more driver's worth of data time.

Every division is rounded down (floor), matching the behaviour of the hardware counter.

Two more things to remember when setting up the scope The red note under the table: A Trigger = TP (rising) and B Trigger = mLVDS CLK (both edges). Set B to a single edge and the count comes out off by a factor of two.

7Result 2: UI cof_cnt boundary setup

The numbers to write into the TCON registers. → Open this card in the tool

Where the boundary values come from

Boundary i (i runs from 1 to the driver count −1):

boundary = floor( Hactive ÷ 2 ÷ drivers ÷ gate × i − 1 )

  • ÷ drivers: split the whole line evenly across the drivers
  • ÷ 2: count in UI (one UI covers two pixel positions)
  • ÷ gate: with Dual Gate each group handles only half
  • − 1: the counter starts at 0

The 2047 in the last row

The last driver (Xn, End) and every row beyond the driver count always show a boundary of 2047. It is not calculated; it is an end marker meaning "all the way to the end" - it tells the TCON there is no further boundary in this segment.

EM02 does not halve 2047 It is a sentinel, not a formula result, so it stays 2047 when you switch to EM02. Seeing it unchanged is the correct behaviour.

Change one cof item and the rest follow Set a row to cof2 and the tool makes the rows below it become cof3, cof4 and so on, then clears any duplicate name on the other rows to -. That way two rows can never point at the same register. To clear a single row, pick -; that does not trigger the chain.

The table has as many rows as "the driver count" or "the number of cof registers on that model", whichever is larger. So EM02 still fills all 7 rows when the driver count is small (the extra rows show - as the boundary position and 2047 as the value).

cksk lane mapping

Used for "non-split (non-time) adjustment: shift CLK only".

CodeMapping lane
lalane 0–3
lblane 8–11

The order of lb and ra is easy to get backwards The table reads la→0-3, lb→8-11, ra→4-7, rb→12-15, which is not a continuous run. Pick the wrong code and you shift the clock of a different lane group.

Coarse (cksk)

Moves setup time in steps of 1/16 UI.

StepSetup Time

Step 0 is a special case whose value is the same as 8; in normal use, adjust up or down from the default of 8. The real time span = the step ratio × 1 UI, and the absolute value of 1 UI can be worked out with the Rx/Tx Frequency Calculator.

Fine

Used for "split (time) adjustment". The unit is real picoseconds (ps) and does not depend on frequency.

The steps are not evenly spaced The gaps between −52 / −31 / −14 / 0 / +11 / +36 / +59 are not equal; that is how the circuit is built. So "two steps earlier" and "two steps later" are not symmetric. When tuning, read the ps value directly instead of counting steps.

9FAQ

Click a question to expand the answer.

Calculate does nothing, or the page jumps to some field?▼

That means a field failed validation. The page scrolls to the first red field. Hactive and X1…Xn must be positive integers, and the event count must be 0 or a positive integer. Calculate is also blocked with a prompt if you did not click "Drivers per Port" first.

The whole result block vanished after I changed an input?▼

That is deliberate. Once an input changes, the numbers already on screen no longer match it, and leaving them there only invites copying the wrong value. Press "▶ Calculate" again. Exception: working inside the result area (switching the TCON model, changing a cof item dropdown) does not clear the results, because those change how the results are presented, not the input conditions.

I switched to EM02 and every boundary halved?▼

Correct. EM02 boundary = EM01 boundary ÷ 2 (rounded down), for example 15 → 7 and 32 → 16. Switch back to EM01 and the original values return; the halving is never applied twice. The one value that never changes is the end marker 2047.

The calculated B event values do not line up on the scope?▼

Check these in order of likelihood:

  1. B Trigger is not set to both edges - a single edge is off by a factor of two.
  2. Single / Dual Gate is wrong - also off by a factor of two across the board.
  3. The starting event count is wrong - A must be the XSTB(TP) rising edge, and you count up to the RST falling edge.
  4. X1 points the wrong way - X1 must be the driver closest to the TCON.
  5. Driver bits / pairs do not match the actual board.
I changed X1 but some Xn fields did not follow?▼

Those fields were edited by hand, so the tool no longer overwrites them with X1 and the values you tuned survive. To force them all the same, press Copy to All: it overwrites the hand-edited ones too and clears the mark. Selecting the driver count again also resets everything.

I changed one cof item dropdown and the other rows moved on their own?▼

This is sequential chaining: cof registers must map in order to the boundaries from nearest to farthest, so once you set a row to cof2, the rows below it become cof3, cof4 and so on, and any duplicate name on the other rows is cleared to -. Picking - does not trigger the chain.
